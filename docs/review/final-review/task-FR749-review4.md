### Minor
1. **Point 2 — a job ALREADY RUNNING at the close, in a queue nobody disposed of, still writes into the library after `close()` resolved** (`packages/library/src/import/proxies.ts:320-387`, same shape in `import/ocr.ts`). Probe D: the worker call held, `close()` awaited, then released. At `close()`'s resolution `.tmp/worker-proxy-…` existed; afterwards the worker wrote its output into it and the queue's `finally` removed the folder, both with the lock gone. The job ended "PENDING", with no record, no unhandled rejection, and the queue stayed usable (a later `enqueue` is refused at once and `idle()` returns `[]`). The engine's close does not wait for media jobs (they are not `inFlight`). Only the service's disposal covers this: `apps/library-service/src/state.ts:1323-1324` awaits `disposeProxyQueue` and then `disposeOcrQueue` (`dispose` waits `idle()`) before `s.lib.close(...)` at :1339. That is the class R562 accepted ("stopped by the service, not by the engine"). R562 asked only that no job be taken or started once the library is closed, and that holds. Noted so the line is known, not for mending here.
2. **Point 5 / point 1: "byte for byte, absence included" does not hold for a state file that existed but was EMPTY (or unreadable)** (`export/backup.ts:576-590`). Probe C1: the state file was truncated to 0 bytes, then a retry attempt ran and the close cut it. Afterwards the file holds the full JSON with empty records. `stateWasAbsent` is false, so `dropIfEmpty` does not apply, and `writeState` reserialises whatever `readState` made of the old file. Every state write before FR-749 did the same, and the meaning (no records) is unchanged. R560 M4 ruled only on the absent file. Cosmetic.
3. **The proxy queue's second guard has no test of its own** (`proxies.ts:312-313`, "asked again after that read"). Planting only the two `runJob` guards and the `enqueue` guard away makes `queues-closed.test.ts` fail (plant D), but those tests close the library before anything starts. No test lands a close during `currentProjectLocationMode`. Judged right by reading: the check comes in the same tick as the `mkdir`.
4. **A doc comment is misplaced in a test file** (`retention-closing.test.ts:463`): the R560 I2 comment block sits above the `describe` for "no state file before a cut retry attempt (R560 M4)", and the I2 `describe` below it has none. Cosmetic.
5. **The guard on the stamp-existence check is outside the manifest queue** (`retention.ts:768`, `backup.ts:1280`): `exists()` is read before the queued write, so another writer can create the file in between. By reading this is harmless: `dropIfEmpty` removes the file only when the state is empty at the put-back, inside the queue. Two cut writers, or a cut writer racing a legitimate one counted in the close's wait, therefore leave the file exactly when it holds something. No probe.
