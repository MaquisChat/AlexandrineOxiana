## NEEDS A RULING

**FR-368 — the chooser checks every 2 seconds while the last library is still opening, without limit.** The limit-less check was instructed (Task 46a: only an explicit choice abandons the attempt), so any limit changes what the researcher sees. Options: (a) leave it (a request to the local service every 2 s costs almost nothing); (b) keep checking until the library opens or the researcher chooses, but space the checks out: 2, 4 and 8 s, then every 15 s — the sentence "it opens here as soon as it is ready" stays true within 15 s; (c) stop after some minutes and say "Thesis library is still not answering. Check again, or choose another library." with a Check again button. Recommendation: (b), no wording change; it keeps the instruction and bounds the rate. (UI file `packages/ui/src/routes/library.tsx:22-23,80-102`; its test would need fake timers.)

**FR-420 — cross-checks read outside the write queue (`reconnect.ts` `checkIntegrity`; `retention.ts` `onDisk`).** Neither is a small change. `checkIntegrity` takes the library, not the repo, so it has no way into the write queue; it is called by reconnect (with a repo just opened by itself — nothing else writes then) and by the service's "check integrity" route (`apps/library-service/src/routes/libraries.ts:388`), where an import or a destruction in progress can make a file look missing or mismatched for a moment. `onDisk` reads certificate and amendment files after the audit view (`scan`) was taken; an amendment written between the two reads is called "named like an amendment … the audit log does not record it". Both would follow Task 70's pattern — on a finding, read again in the queue's turn and report only what is still there — but `scan` itself enters the queue (`auditEventsMentioning`), and the queue is not re-entrant (only `holdsTurn` lets a read skip it), so the retention re-check needs an in-queue variant of `scan`, and `checkIntegrity` needs an optional `confirm(fn)` (the repo's queue) passed by the service, re-checking only the flagged entries against a fresh read of their source. Recommendation: build both that way as a small task of its own, with the reviewer probing the queue (deadlock, long turns: re-check only flagged entries, never re-hash the sample in the turn).

**FR-423 — every read of a source with a REAL mismatch waits for the write queue, so in practice through a whole restore.** `sources.ts:151` confirms a problem in the queue's turn; a restore holds the queue for its whole length. Making it not wait means a choice: (a) confirm only when a write of the same project is in the queue (needs the queue to know per-project turns — a locking change); (b) wait for the turn at most a bounded time (say 2 s), then report the mismatch as found (a rare false warning comes back while a long write runs); (c) wait at most that time, then return the read without a warning and confirm later in the background. Recommendation: (c) — it never makes a false warning and never blocks a screen behind a restore — but it changes locking behaviour, so it is not done in this round.
