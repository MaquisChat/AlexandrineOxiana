# Task FR-A16 — a destruction certificate is true about old copies of the library (Ruling R379)

Worktree: `/home/user/AlexandrineOxiana/.claude/worktrees/agent-a7f301291240d4274`, branch `fr-a16-old-copies`. Report: `task-FRA16-report.md`. Common brief first: `/home/user/AlexandrineOxiana/.superpowers/sdd/PLAN/task54-fix-common.md`.

## What is wrong (review: `/home/user/AlexandrineOxiana/.superpowers/sdd/PLAN/task54-wb2-review.md`, finding I2, and its answers on the Task 13 points FR-069/FR-070 — read them)
When a project's retention rule says its data must be destroyed, the app overwrites and deletes the project's files and writes a CERTIFICATE of destruction (`packages/library/src/retention.ts`, `repo/destroy.ts`, `destruction-record.ts`). The certificate ends: "This certificate covers the copies this app manages." (`DESTRUCTION_NOTICE`, `retention.ts` about :134). The destruction looks at the project's files, strays in `.tmp`, and the app's own BACKUPS — for backups that still hold the destroyed data it has a careful mechanism: the certificate lists them, and the project carries a standing warning `destruction-backups-pending` with notes until they are gone (Rulings R147, R175, R90 d — read them: `grep -n -E "^R(147|175|90)\b" /home/user/AlexandrineOxiana/docs/handoff/LEDGER-INDEX.md`, then the full rulings in LEDGER.md; and read how it is built: grep `DESTRUCTION_BACKUPS_PENDING_WARNING` and `destruction-backups-pending` in `packages/library/src`).
But the app also makes and keeps listed OLD COPIES of the whole library: after "Move library" the old folder is kept, read-only, until the researcher confirms its deletion (`packages/library/src/move.ts`, `old-copies.ts`: the list `pending-old-copies.json` in the app's configuration folder; an offer that expires after 24 hours stays in the list, and the folder stays on disk — "Delete it by hand"). The destruction never looks at that list. So a project destroyed under its retention rule is recorded and certified as destroyed while a complete copy of its original files sits in a folder this app made and still lists — and the certificate's last sentence is untrue.

## What to build — mirror the backups' mechanism, do not invent another
1. **At a destruction, find the old copies that still hold the project.** From the app's list of old copies (every record of THIS library's id, expired or not), those whose old folder still contains the destroyed project's folder (or, for a destruction of single sources, those sources' files — read what a destruction can cover and handle each scope the way the backups' check does). A list that cannot be read (`OldCopiesUnreadableError`) is not "none": say so in the certificate and the warning ("could not be checked") — fail towards the warning, never towards silence. An old folder that is not reachable (an unplugged disk) counts as still holding it.
2. **The certificate says it.** In the certificate's text and in its machine-readable record, exactly as pending backups are said (same section style, same tense): how many old copies of the library left by a move still hold the destroyed data and were NOT destroyed, each named by the date of the move that left it (not by its absolute path: a certificate is a file of the library and may be exported; the rule is that no absolute path is stored in the library). The last sentence stays, and is now true because the copies not covered are named.
3. **A standing warning until they are gone.** The project carries a warning of its own, `destruction-old-copies-pending`, built exactly as `destruction-backups-pending` is (where it is raised, stored, cleared, shown; the notes behind it; how a restored copy of the project inherits it — read `backup.ts` and `restore-record.ts` for what "inherits" means there and say what you did for this one). It clears when every such old copy is deleted through the app ("Delete the old copy" after a move) or no longer holds the data (checked when the project's warnings are computed, as the backups' is — cheaply: say what is checked and when). The sentence a researcher reads for it, exactly: "Old copies of this library, left by a move, still hold data that was destroyed here. Delete them from the Move library screen (or by hand) to complete the destruction." — put it where the backups' sentence lives and show it wherever the backups' warning is shown (the audit screen? the project's notices? find every place and list them).
4. **Deleting an old copy through the app** (the existing confirm-and-delete of an old copy) clears the warning for the projects it concerned and writes the same kind of audit entry the backups' removal writes for a completed pending destruction (read what R147 requires for backups and mirror it; if R147 requires an addendum to the certificate when the last copy goes, do the same).
5. Nothing else changes: a destruction is never REFUSED because of an old copy; a library that was never moved behaves byte for byte as before (existing tests unchanged).

## Tests first (each seen to fail first; the move's and the destruction's existing tests show how to make a moved library and a due project in a temporary folder)
- A library moved (old copy pending), then a project destroyed under retention: the certificate names one old copy by the move's date and holds no absolute path (assert on the whole text and record: neither root appears); the project has the warning with its note; the old copy's project folder still has its files (the destruction did not touch it).
- The old copy deleted through the app's own action: the warning clears; the audit entry is written; the certificate's addendum if R147 has one for backups.
- An expired old copy (older than 24 hours) still counts. An old copy of ANOTHER library does not. An old copy that no longer holds the project's folder does not. An unreadable list → "could not be checked" in the certificate and the warning raised.
- A split move (only some projects moved; `move.ts` about :771–786): the moved project's folder left in the old root counts for that project.
- A library never moved: certificate and warnings exactly as before.
- The service: the route that returns a project's warnings returns the new one with its sentence (one test).
