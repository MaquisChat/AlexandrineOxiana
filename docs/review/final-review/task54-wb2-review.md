## Findings

### C1 — Locking (or unlocking again) an encrypted project while a change is being committed seals that change's change-log lines under an all-zero key, and the change commits

- Where: `repo/mutate.ts:486-491` captures `core.key(st).key` (the KeyRing's own buffer, not a copy: `repo/state.ts:214-219`, `crypto/keys.ts:275-278`) into the `seal` closure after `fn` has run; then awaits (`tx.guard` ×2, `appendChanges` with mkdir/open/fsync) before `appendChanges` calls `seal` for each line (`repo/changelog-store.ts:21-26`). `lockProject` (`repo/projects.ts:474-483`) is synchronous, outside the write queue, and `KeyRing.remove` zero-fills that buffer in place (`crypto/keys.ts:288-291`); `KeyRing.add` does the same to the old buffer when the same key is added again (`crypto/keys.ts:271`), which every unlock of an already-unlocked project does (`repo/projects.ts:237-241`; `unlockProject` has no "already unlocked" check). The service's lock route calls `s.repo.lockProject(id)` at once, without waiting for in-flight changes (`apps/library-service/src/routes/projects.ts:164-169`); background work (bulk import, watched folders, Find, attachments) can be mid-commit at that moment.
- Probe 1 (a change recording `note: "Participant Jane Doe, Leeds"`, `repo.lockProject` fired on the next macrotask after `fn` returned): the change committed (allow event written); its change-log line **opens with a 32-byte zero key** (`{"…","field":"/note","prev":"before","value":"Participant Jane Doe, Leeds"}`) and **does not open with the project's real key**; the project is locked afterwards.
- Probe 3 (same, but the KeyRing re-adds the same key, as a second unlock does): zero key opens the line, real key does not, project still unlocked.
- Why it matters: the participant data the change log holds sits on disk under a publicly known key (privacy breach in an encrypted project — readable by anyone with the folder, a sync provider, a backup), and the project's own history line is unreadable with its key (corruption presented as committed). Rules: R25, R30's intent, R26 ("no partial state presented as real"), the "identity never leaves" rule.
- Same class, rolled back today but fragile: `repo/watch-register.ts:303-304` and any `tx.key()` captured before an `await` inside `fn` — the post-`fn` `core.key` check (mutate.ts:488) throws `ProjectLockedError` and rolls back, but the rolled-back file encrypted under zeros is removed with a plain `rm` (`txn.ts:206`).
- Direction: `core.key()` must hand out a copy that the caller zeroes (or seal only from a key read synchronously at the moment of sealing); `lockProject` (and a repeat unlock) should go through the write queue (`core.serial`) so it never lands inside a commit; `KeyRing.add` of an identical key should keep the existing buffer; a test that locks during a commit and checks every line opens with the real key. No FR point covers this (grep `lockProject`, `zero`, `KeyRing` in final-review-list.md).

### I1 — Absolute paths are stored in the library: the job journal records each worker job's absolute input and output paths

- Where: `worker-client.ts:423-431` stores `StoredJob { input: job.input, output: job.output }` in every pending journal line (`<Project>/jobs/journal.jsonl`, `job-journal.ts:46-53`, appended at `worker-client.ts:443-447`). The callers pass absolute paths: `import/proxies.ts:308,320` (`join(root, asset.path)` or `asset.linked.absolutePath`; output `join(root, ".tmp", …)`), `import/ocr.ts:240-245` (same), `transcription-jobs.ts:66-68, 101-103` (`join(repoLibrary(repo).root, …)`). `WorkerJob.input` is documented as "Absolute path of the input file" (`worker-client.ts:62`).
- In an unencrypted project these lines are plaintext (only encrypted projects seal them, `job-journal.ts:7-9`); a line stays until compaction keeps only the newest line per job. The journal moves with the library, so the paths name the previous computer's user folder and the previous library location after a move or copy.
- Rule: SPEC line 207 ("No absolute paths are stored in the database, source.json, or any other library file", the only exception a *linked* file's own path in its asset record); the standing rule in the common brief. Not in the FR list (only FR-229, a route carrying `linked.absolutePath`).
- Direction: store library-relative input/output (and the asset id) in the journal, resolve to absolute at run time — transcription-jobs already recomputes the input on resume (`extras.input`), so the stored value is not even needed there.

### I2 — A destruction under retention says it covers "the copies this app manages" while an old copy of the library that the app made and keeps listed still holds the destroyed originals

- Where: `retention.ts:134-135` (DESTRUCTION_NOTICE: "This certificate covers the copies this app manages."); the destruction considers the project's files, `.tmp` strays and `Backups/` (`retention.ts:302-372`, `repo/destroy.ts:97-150`) but never the app's own record of old copies (`old-copies.ts`; no reference to it from `retention.ts`/`destroy.ts`). After a move, the old copy is kept read-only until the researcher confirms deletion; after 24 h the offer expires and it is kept for good ("Delete it by hand", `move.ts:112-120`; FR-069/FR-070 never prune), and in a split move every moved project's folder stays in the old root with its originals (`move.ts:771-786`).
- Effect: a project destroyed under its retention rule is recorded as destroyed (certificate, `retention.destroyed` event) while full copies of the raw identifiable originals remain in a folder this app created and still lists, and the certificate's last sentence is untrue. Rule: R90 d, R147 (never recorded as destroyed while it remains in what the app manages).
- Direction: at destruction, look up pending old copies of this library (by library id) that hold the project's folder and either list them in the certificate as copies not destroyed (with the warning `destruction-backups-pending`-style until they go) or refuse until the old copy is deleted; the notice's wording made true either way.

### Minor

- M1 `repo/destroy.ts:128` — stray `.tmp/trash-*` copies are shredded inside `fn`, before the commit and outside the write-ahead marker: if the change then rolls back (certificate write, change log or audit append fails, a crash), those copies are destroyed with no certificate and no event. `strayCopies` (`retention.ts:259-285`) matches by base name across every project's orphan trash, so another project's leftovers with the same file name are destroyed and listed in this project's certificate. Direction: `tx.destroy` them (move under the marker, shred after commit) and match only this project's asset paths.
- M2 `repo/projects.ts:474-483` — locking is neither audited nor serialised, while unlocking is audited (`repo/projects.ts:242-247`); the audit record shows when a project was opened but never when it was closed. (Serialising it is part of C1's direction.)
- M3 `repo/collections.ts:296-303, 330-345` — creating a workspace tag is not evaluated by the policy engine, not audited, and not under the marker (tags.json is written, then the plaintext root change log; a crash between them leaves an unlogged change; a failed undo of tags.json is swallowed nowhere — it throws the second error and loses the first). R25 accepted the root change log, not the missing decision and audit.
- M4 `transcript-segments.ts:406-414` — a researcher's edited transcript of an encrypted project is written in plaintext to `.tmp/worker-edit-*/transcript.vtt` before `addDerivedAsset` encrypts it; after a crash the leftover is removed at the next open by a plain `rm` (`repo/repo.ts:517`), never overwritten. The worker's decrypted inputs (`worker-client.ts:465-470`) are the same. Direction: write the edit through `encryptBytes` into the work folder (sealed) or shred leftovers of encrypted projects.
- M5 `library.ts:152-162` (FR-071, graded D) — a moved-away project folder counts as live again when its project.json is newer than its MOVED.json; copying an old library with a tool that does not keep times (cp without -p copies "MOVED.json" before "project.json") revives the project in the remaining library while the same project id lives at the destination — two writable copies of one project with diverging audit chains. Still Minor; noted because it is more than "validity depends on mtimes".
- M6 `crypto/keys.ts:26` — a key file's scrypt cost is accepted down to 2^10 (the test value); a project made by a test build, or a key file edited, unlocks at 1/128 of the intended cost with no warning. Direction: refuse or warn below 2^15 outside test mode.

## Checked and sound

- `runMutation` order (decide → marker → files → change log → audit → marker delete) and its in-process rollback; a deny is audited before anything is written and thrown; `unauditedDeny` only for the bulk fallback (R62 M).
- Marker validation (`markerProblem`, `unsafeOnDisk`): every path confined lexically and through links to its own project folder, backups/trash named for the transaction; a marker naming one project and pointing into another blocks both.
- Recovery decision: committed only when every allow event of the txn is in the log; rollback only when the prefix verifies, the anchor is not past the start, and the recorded append offsets still sit on line boundaries with exactly the recorded count before (R131 b).
- `TxnLog.trashed` dropping appended/newDir entries under the trashed path (R62 (1)); EEXIST retraction of a folder step.
- Destroyed files are shredded after the commit and before the marker goes; a failed shred keeps the marker (`committed-destroy-pending`) and the trash.
- Two changes at once: one write queue per repo (`serial`), every mutation re-checks writability, recovery-pending and lock inside its turn.
- The library lock: settle-and-re-read, staleness by heartbeat and dead pid, release only if ours; lost-lock flips read-only (R21's documented cross-sync window).
- Key wrapping: scrypt with bounded parameters, keyId in AAD, KEK zeroed; `encryptStream` copies its key at creation; decryption with a zeroed key fails closed.
- deleteOldCopy: holds the old copy's lock, deletes only files whose hash equals the verified one, keeps library.json/MOVED.json while anything is left, never follows a link.
- Service error mapping scrubs paths from `LibraryMovedError` and integrity-warning details.
