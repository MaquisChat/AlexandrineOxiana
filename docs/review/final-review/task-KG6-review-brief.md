### FR-731 — Quit on a Mac (commit d9a3921), by reading the PINNED sources
The shell now takes the Mac's quit request and ends the app "the way SIGTERM does". Sources: `apps/desktop/src-tauri/Cargo.lock` for the versions; `~/.cargo/registry/src/*/` (`tao-*`, `tauri-2.*`, `tauri-runtime-wry-*`, `muda-*`, `objc2*`/`cocoa*` whichever is used).
1. HOW is the request taken — a method added to or swizzled on tao's application delegate (`applicationShouldTerminate:`), an Apple-event handler for the quit event, a replaced menu item? Is that mechanism sound at the pinned versions: the delegate class tao registers (its name, whether it already implements the method, whether adding or replacing a method on it at run time is safe, whether tao sets its delegate before or after the shell's code runs, whether a later tao call re-installs its own); the Objective-C signature and return type (`NSApplicationTerminateReply`: an enum of machine word size — a wrong return type is a crash or a wrong answer only on a real Mac); the thread (the main thread only); `unsafe` blocks and what each assumes; memory (a block or selector kept alive). Every `unsafe` line gets a sentence in your report.
2. The answer given: cancel the terminate and start the shell's own orderly exit — then the app must really end: the orderly exit asks for exit (which path: `app.exit`, the SIGTERM handler's code?), `RunEvent::ExitRequested` prevents it, the helpers stop, the closing window shows after two seconds, then the process exits. Can the app's own final exit call go back through `terminate:` and be CANCELLED AGAIN by the new handler — a loop, or an app that can never quit? What marks "we are already closing" and is it set before the first cancel returns? A second Cmd-Q during the closing; Cmd-Q while the closing window is frontmost; Cmd-Q during start-up before the helpers are up; Cmd-Q after a failed start (the error window): each ends the app, once.
3. R505 e: a quit asked for by the SYSTEM (logout, restart, shutdown) is left as it was — answered "now". How does the code tell that case (the Apple event's quit reason? which API, is it reliable at the pinned SDK, what is the default when the reason cannot be read — the safe default for a logout is "now"; the safe default for Cmd-Q is the orderly way: which wins when unsure, and is that what R505 e rules)? Is the app's standard menu intact (About, Hide, the Edit menu's Copy/Paste/Select All, Window) — was the menu touched at all?
4. Nothing changed on Linux and on the other ways to end (the window's close button, SIGTERM, SIGINT, a second launch's hand-over, a failed start): the new code is `#[cfg(target_os = "macos")]` in every line, and the Linux build's behaviour is byte-for-byte the old path (diff the non-Mac lines).
