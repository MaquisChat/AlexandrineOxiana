## What is wrong
The owner imported their Zotero library. In the review queue an item says: "Title — Conflict. Two sources disagree about the title: 'Subsistence and persistence: agriculture in the Central Plains of China throu…' (from Zotero) versus 'S0003598X20000800jra 900..915' (from the file's embedded data). Confidence 60%, from reference-metadata." The second "title" is a publisher's production code left in the PDF's information fields. Of the first 170 items imported, 55 went to review — in a library of thousands that is hundreds of pointless reviews.
How it happens: when a file is imported, `resolveItem` (`packages/library/src/import/resolve.ts`) gathers what is known about it in steps — the reference manager's record (Zotero), then the file's EMBEDDED metadata (for a PDF: the Info dictionary's Title and the XMP `dc:title`, read in `packages/library/src/extract/pdf.ts`), and so on — and when two sources give different titles it records a conflict and sends the item to review (find `titleConflict` and where the reference title and the embedded title are compared; read the whole function first). The only filter on embedded titles is `JUNK_TITLE` in `extract/pdf.ts` (:20): "untitled", "Microsoft Word - …", or a name ending in a document extension.

## What to build
1. **One rule, "this embedded text looks like a title", in one place** (a small module in `packages/library/src/extract/`, or in `packages/core` if the screens need it), used for EVERY kind of file whose embedded title is read (find them all: `grep -rn "title" packages/library/src/extract/*.ts | grep -v test` — PDF Info and XMP, Word and OpenDocument core properties, EPUB/OPF, images' XMP/IPTC, audio and video tags; say for each kind whether its embedded title is filtered and why). An embedded title is DROPPED at extraction — it is not the item's title, not evidence, not a conflict, and nothing mentions it — when, after trimming and folding white space:
   - it holds no word made only of letters with three or more letters (any script; in a script written without spaces, two or more characters count as a word) — "S0003598X20000800jra 900..915", "JQE-2020-0041.R1", "12345", "doc1";
   - or it is an identifier: a DOI (`10.` + digits + `/`…), an ISBN or ISSN, an arXiv number, a publisher's item code (a letter followed by fifteen or more digits and letters), a UUID, a run of sixteen or more hexadecimal digits, a run of letters and digits mixed of twelve or more characters with no space;
   - or it is a file name (it ends in a known file extension, or holds a path separator) or the file's own name without its extension (compare without regard to case; pass the file's name in where the rule is called);
   - or it is one of the stock texts programs leave there, alone or followed by a number: untitled, document, new document, presentation, powerpoint presentation, slide 1, title, layout 1, blank, scan, scanned document, print, full text, front matter, back matter, cover, table of contents, index, "Microsoft Word - …", "Microsoft PowerPoint - …", "Adobe Photoshop …" (keep the existing three patterns; make the list one constant, in English only, and say that other languages' stock words are not covered);
   - or more than half of its characters are digits and punctuation.
   A title of ONE plain word ("Persuasion", "Middlemarch") is kept. A real title that begins with a number ("1984", "2001: A Space Odyssey", "100 Years of Solitude") is kept — test them: "1984" alone has no letters… decide by this: a title of digits only, of four or fewer digits, is kept ONLY when the file gives nothing else to contradict it — simpler and safer: it is dropped as an embedded title (the reference manager or the file name will name such a work); say so in the comment.
2. **An embedded AUTHOR that is a stock name is dropped the same way** (in the same module): administrator, admin, user, owner, author, unknown, anonymous, a single word ending in "PC" or "Laptop", the names of scanners and typesetting or office programs when they stand in the author field (find what the extractors put into creators and test with: "Administrator", "User", "Owner", "CamScanner", "Adobe InDesign", "LaTeX with hyperref", "Microsoft Office User", "TeX"). A real person's name is never dropped: the list is exact words, compared without regard to case.
3. **Agreement before conflict** (where the reference manager's title and the embedded title are compared in `resolveItem`): after folding case, accents, punctuation and white space, the two AGREE when they are equal, when one begins with or contains the other and the shorter has at least three words (a running head; a title without its subtitle; a title cut off by a length limit), or when the existing similarity measure already says so (keep its threshold). Only a title-like embedded title that clearly names another work remains a conflict — keep one such case as a test: it is worth the researcher's look (the wrong file may be attached to the record). The item's title stays the reference manager's in every case, as now.
4. **Nothing else changes:** a file with NO reference record still takes a good embedded title as its title (and a dropped junk title leaves it to the later steps: the first pages' text, the file's name) — test both; identifier look-ups, the confidence numbers of the other paths and the review rules for other fields are untouched.
5. **Entries already waiting for review** for this reason are not changed by this task. Find out and say in your report what a LATER import of the same Zotero library does with an item that is waiting for review (is it passed by, updated, or evaluated again?), so that the owner can be told what to do with the fifty-five they have.
