## Attack hardest
1. **An ordinary crash must still be undone completely.** Nobody touched anything by hand: for every kind of change the app makes (import a file by copying, by linking; add a derived file; a transcript's two files; save annotations; edit a record; delete a source; merge; move a source to another project; a watched file brought in; Find's attach; a restore; a retention destruction), a crash at every step, then the reopening: the undo is COMPLETE and the library is as before. The new rules must never call the change's own bytes "not its own": a file half-written (no completion line); a file completely written whose completion line was not yet written (the crash fell between the two: what does the undo see — a file with no completion line → "half-written" → removed: right); a completion line written and the file then touched by the SAME change again (a second write to the same path in one change: which hash stands?); an encrypted project (the stored bytes are what is hashed: prove the hash is of the bytes on disk, taken in the same pass, for a streamed copy larger than one chunk, and that a locked project's undo at the opening — no key — still judges by stored bytes without needing the key); a file whose mode or times changed but not its bytes. Use the existing crash seams of the tests; where the enumeration (`rollback-rerun.test.ts`, the new hand-put enumeration) already covers a case, say so and try the neighbours it does not.
2. **A person's file is never destroyed** — the property the task claims for created, replaced and trashed lines. Try to break it: a hand-put file at a created path BEFORE the change's own write landed (the change then overwrote the person's file: whose bytes are "the change's own" now, and what did the completion line record?); a hand edit that keeps the size; a hand-put file that is byte-for-byte what the change wrote (then removing it destroys nothing: is it removed, and is that right); a symbolic link or a folder put at the path; a hand-put file inside a folder line's folder that a later line names; the same path named by three lines. And the two places R525 says are NOT covered (a file the change only appended to; an unnamed file inside a folder the change created) — do not report those; DO say if anything ELSE is uncovered.
3. **The replaced-file change (R525 point 1)** — the implementer extended the protection to files the change REWROTE, superseding R473/R484 ("the earlier state is put back all the same"): a hand-changed rewritten file is no longer overwritten; the undo is incomplete.
