## What is wrong (review: `/home/user/AlexandrineOxiana/.superpowers/sdd/PLAN/task54-wb2-review.md`, finding C1 — read it whole, with its two probes and its "same class" paragraph)
An encrypted project's files are sealed with the project's data key, held in memory in a key ring (`packages/library/src/crypto/keys.ts`) while the project is unlocked. `core.key(st)` (`packages/library/src/repo/state.ts` about :214) hands out the key ring's OWN buffer, not a copy. `KeyRing.remove` (lock) zero-fills that buffer in place; `KeyRing.add` of the same key again (every unlock of an already-unlocked project, `repo/projects.ts` about :237) zero-fills the old buffer. `runMutation` (`repo/mutate.ts` about :486) captures the key into a closure and then awaits several times before the change-log lines are sealed. `lockProject` (`repo/projects.ts` about :474) is synchronous and outside the write queue; the service's lock route (`apps/library-service/src/routes/projects.ts` about :164) calls it at once. So a lock (or a second unlock) that lands while a change is being saved makes that change's change-log lines be sealed under an ALL-ZERO key — readable by anyone with the folder, unreadable with the project's key — and the change is still recorded as saved.

## What to build (Ruling R379, FR-A13 — read it in full)
1. **No holder of a key can have it wiped under them.** Choose the smallest sound design and say which: (a) `core.key()` (and `tx.key()`, and every other accessor that hands a key out — list them all: `grep -rn "\.key(" packages/library/src/repo packages/library/src --include=*.ts | grep -v test`) returns a COPY that the caller's scope wipes when it ends; or (b) sealing reads the key synchronously at the moment of sealing and never across an `await`. Whichever: after your change, no code path seals or encrypts with a buffer that `remove`/`add` can zero meanwhile. A wiped key must be IMPOSSIBLE to seal with: add a guard in the one sealing/encrypting primitive (`sealLine`, `encryptBytes` in `repo/io.ts`, or lower) that refuses an all-zero key with an error — a last line of defence, tested.
2. **A lock waits its turn.** `lockProject`, and an unlock of an already-unlocked project, go through the project's write queue (`core.serial` or what `runMutation` uses — read how changes are serialised), so that neither can land inside a change being saved: the change either completes with the real key before the lock, or starts after it and is refused as locked (`ProjectLockedError`), fully rolled back, with nothing written under any key. The lock still answers promptly (it waits only for the change in progress, not for the queue behind it — say what you built and what a long-running background job (a bulk import, a watched folder, Find) means for the wait: each of its changes is one turn).
3. **Adding the same key again keeps the existing buffer** (`KeyRing.add`): an unlock of an unlocked project changes nothing and wipes nothing.
4. **The same class** the review names: `repo/watch-register.ts` about :303 and any `tx.key()` captured before an `await` inside a change's function; and the rolled-back file that was encrypted under zeros and is removed with a plain `rm` (`txn.ts` about :206) — with point 1 there is no such file any more: show it by a test.
5. Nothing else changes: the key is still wiped from memory at lock (the ring's buffer is zeroed; copies are wiped by their holders — show by a test that no copy outlives its change: e.g. count live copies through a test seam, or assert the buffer handed to a finished change is zeroed afterwards).
