## What happened
The project is a desktop app (Tauri 2 shell; a local Node service; a Python "media worker", packaged with PyInstaller 6.22.3 as a one-folder bundle `ao-worker/` and shipped inside the app). The project's owner runs the Mac build (Apple Silicon; built on GitHub's `macos-15` machine with `actions/setup-python` 3.13). On the Optional tools screen, "Speech model: tiny" → Install answered: "Installing did not finish. The download did not finish. Check the internet connection, then try again." (the owner had a VPN on).

That sentence is the service's wording (`apps/library-service/src/routes/tools.ts`, `MESSAGES.TOOL_DOWNLOAD_FAILED`) for the worker's code `TOOL_DOWNLOAD_FAILED`, raised in `services/media-worker/ao_worker/fetch.py` for several different failures. Every optional-tool download (speech models, ffmpeg, OCR, yt-dlp and its release list in `download.py`, gallery-dl) goes through `fetch.py`'s `_WatchedHTTPS`, which is `urllib.request.HTTPSHandler()` with the standard library's DEFAULT TLS context. That context reads its certificate authorities from the OpenSSL default paths compiled into the Python of the build machine. PyInstaller has no hook that points the standard library at a list inside the bundle (`hook-certifi` only copies certifi's `cacert.pem`, which `requests` uses, not `urllib`), and the worker sets nothing. Off the build machine those paths do not exist → no authority is trusted → every certificate fails → `URLError` → `TOOL_DOWNLOAD_FAILED`.

Reproduced on this Linux machine by the coordinator, with the worker's real `fetch.download` on the pinned `config.json` of the tiny model: normal environment → `OK 2249 bytes`; with `SSL_CERT_FILE=/nonexistent/cert.pem SSL_CERT_DIR=/nonexistent/certs` → `TOOL_DOWNLOAD_FAILED | the download failed (no connection) | detail: URLError | cause: [SSL: CERTIFICATE_VERIFY_FAILED] … unable to get local issuer certificate`. (The probe: `/tmp/claude-0/-home-user-AlexandrineOxiana/ac3b5cb4-f467-5f83-9948-4e7d2e34f036/scratchpad/dl-probe.py`, run with `PYTHONPATH=<worktree>/services/media-worker`. This machine reaches huggingface.co through a proxy that re-signs TLS and whose authority is given by the environment's `SSL_CERT_FILE` — so here the machine's default store MUST stay trusted, or nothing downloads.)

Nobody here has a Mac, and the Mac build runs on the build machine, where the default paths exist. So the fix must be provable on any machine.

## What to build (four points, one commit each, tests first)

### (a) The worker's own certificate authorities
One function in `fetch.py` (say `tls_context()`), used by `_WatchedHTTPS` and so by every caller (`download.py`'s release lookup uses `fetch.watched_handlers`): `ssl.create_default_context(cafile=<certifi's file>)` — certifi's list, which is inside the bundle — and then IN ADDITION the machine's default store (`context.load_default_certs()`: it honours `SSL_CERT_FILE` / `SSL_CERT_DIR` and silently skips paths that do not exist). Certificates and host names stay verified exactly as today (never `CERT_NONE`, never `check_hostname = False`). If certifi's file cannot be found or read, fall back to the default context and log one warning (a download must not fail for THAT reason where the machine's store would have worked) — and (c)'s self-check then fails the build.
- certifi becomes a DECLARED dependency in `services/media-worker/pyproject.toml`, pinned exactly at the version resolved today (`2026.10.23` in both the worker's venv and the build venv on this machine — verify), with a one-line comment why; no other version may change. Check `packaging/constraints-macos-x86_64.txt` (the Intel pin set: does it need a line? only if it would otherwise resolve differently), `packaging/dists.py` / `manifest.py` (the licence manifest: certifi is MPL-2.0 — is it already listed as a run-time distribution through `requests`? it must still be, once), and any test that pins the list of declared dependencies or licences.
- Tests (pytest, `services/media-worker/tests/`; read how the existing `fetch` tests run a local HTTPS or HTTP server and follow their style): with `SSL_CERT_FILE` and `SSL_CERT_DIR` pointing at paths that do not exist (monkeypatch the environment), the context `fetch` uses has certificate authorities (`cert_store_stats()["x509_ca"] > 0`) — failing first against today's code; the context still verifies (`verify_mode == CERT_REQUIRED`, `check_hostname is True`); `_WatchedHTTPS` really uses that context (not only the helper); a server presenting a certificate signed by nobody trusted is still REFUSED (if the existing tests have a TLS fixture; if making one needs the `cryptography` package, it is in the venv — keep it small); the fallback when certifi's file is missing.

### (b) A certificate that cannot be verified is told apart from "no connection"
- Worker: where `fetch.py` turns an opening failure into `TOOL_DOWNLOAD_FAILED` "the download failed (no connection)", a failure whose cause is `ssl.SSLCertVerificationError` (directly, or as a `URLError`'s `reason`; also when it surfaces while reading the body, or on a redirect's new connection) raises a NEW code `TOOL_DOWNLOAD_UNTRUSTED`, message "the download was refused: the server's certificate could not be verified", detail = class names only (for instance `URLError/SSLCertVerificationError`), never an address. For the other opening failures make the detail name the inner class too (`URLError/gaierror`, `URLError/TimeoutError`, `URLError/ConnectionRefusedError`) so that a log tells them apart. `download.py`'s own yt-dlp paths (about :150–205) that turn failures into `TOOL_DOWNLOAD_FAILED`: the same distinction where they open a connection.
- Service (`apps/library-service/src/routes/tools.ts`, `MESSAGES`): `TOOL_DOWNLOAD_UNTRUSTED: "The download was stopped because the secure connection to the publisher could not be verified, so nothing was installed. A VPN, a security program or a network that inspects secure connections can cause this: try again without it, or on another network."` — exactly this sentence.
- Shared type (`packages/shared/src/api/tools.ts` about :108) gains the code; the interface's own list of sentences for a capture that needs a tool (`packages/ui/src/api/capture.ts` about :236, where `TOOL_DOWNLOAD_FAILED` has the sentence "A tool could not be downloaded. …") gains: `"A tool could not be downloaded because the secure connection to its publisher could not be verified. A VPN, a security program or a network that inspects secure connections can cause this: try again without it, or on another network, from the Optional tools screen."` Find every other place that lists the worker's tool codes (`grep -rn "TOOL_DOWNLOAD_FAILED" --include=*.ts --include=*.tsx --include=*.py --include=*.rs packages apps services e2e`) and treat the new code alike (a retry offered where the old one offers it; nothing that treats an unknown code as "not a tool error").
- Tests at each layer, failing first.
