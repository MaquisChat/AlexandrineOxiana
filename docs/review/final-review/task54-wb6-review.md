### Important

**I1 — The Governance screen shows rules the policy engine cannot read as if they were in force, with no warning.**
`packages/ui/src/screens/GovernanceSettings.tsx:124-157, 289-293`; `screens/governanceModel.ts:179-186`; service `apps/library-service/src/routes/governance.ts:71-84`.
The service's GET swallows a core parse failure ("unreadable rules: every request is denied") and answers `violations: []`. The screen parses with its own lenient `readConfig` (YAML + merge onto defaults, no schema), so a file with an unknown key, a wrong type or a bad enum value displays as a normal set of rules. Probe (deleted): `governance.yaml` = `encryption: {atRest: optional}` + `residencey: {allowed: [local]}` → core `parseGovernance` throws "governance.yaml is invalid"; rendered screen: `alerts: []`, no `.ao-warning`, every card shows values, "Save changes" disabled. Meanwhile every capture, import, change and export in that project is refused. The Capture screen's policy (`api/capture.ts:133-145`, `readable: false`) and the import policy (`api/import.ts:315-324`) fall back to strict silently too — no screen says the rules cannot be read. Breaks R58's intent (governance-load problems surfaced on the governance screen) and "governance fails closed" being visible; a researcher meets a wall of refusals with a screen that says the rules are fine. Direction: let GET say `readable: false` with the core's issues (and the non-fatal `parseGovernanceWithWarnings` warnings), and show them as an alert on the screen. Not FR-125: that point is the non-fatal warnings only (triaged D on "waives nothing").

**I2 — The library move's own warnings (lost audit events among them) are dropped by the screen.**
`packages/ui/src/screens/MoveLibrary.tsx:119-123` (and the cut-off path `:59-70`).
The `done` line carries `result.warnings` (service `routes/libraries.ts:256`, scrubbed). They come from `library/src/move.ts:887-924`/`:845-876`: "The library.move audit event could not be recorded for project X …; it could not be kept for later either", "… is marked as needing attention", plus split-audit failures. The screen ignores them and says only "All N files were copied and verified." The plan's per-project `decision.warnings` are also not shown (`:214-221`). The cut-off path (`pickUp`, `/libraries/move/status`) has no warnings at all to show. An unrecorded audit event of a governed change, hidden from the researcher, is a governance/audit gap. Direction: show `result.warnings` (and plan decision warnings) in the result; keep them in the pending move so the status route can return them.

**I3 — Fieldwork: a doubled submit or a held key creates permanent duplicate records.**
`packages/ui/src/screens/Fieldwork.tsx:125-139` (`run` has no in-flight guard), `:192` (Add participant: no `disabled={busy}`), `:231-245` (Add session), `:370-379` (Add consent record).
Probe (deleted): two `submit` events on the consent form and two clicks on "Add participant" → `POST consent`, `POST consent`, `POST participant`, `POST participant`. Consent records can never be deleted ("kept as evidence", `routes/fieldwork.ts:132-134`), so a doubled Enter leaves a second consent record for the participant for good — and withdrawing one leaves the other saying consent stands. Each extra participant uses and retires a code for ever (R117). This is the FR-630 hazard (a held or repeated key fires twice) on controls outside FR-A9's list. Direction: one request at a time (a ref like `KeyField.run`), forms and the button disabled while it runs.

**I4 — Fieldwork deletes a session at one press, with no question.**
`packages/ui/src/screens/Fieldwork.tsx:224-226`; the file's own header (`:6-7`) says "A participant or session can be deleted only when nothing links to it (asked first)".
Probe: one click on "Delete the session of 2026-01-02" → `DELETE session`, no dialog. The session's date, place and notes (fieldwork details) are gone; the change is audited but nothing in the screens restores it. Focus then falls to the page body (the button unmounts). Direction: the same `ChoiceDialog` as Delete participant (with FR-A9's heading focus), focus to the Sessions heading after.

**I5 — Move library: a connection lost before the service's answer says "Nothing was copied or changed" while the move may run.**
`packages/ui/src/screens/MoveLibrary.tsx:129-137`; service `routes/libraries.ts:185-202`.
The service sets `moving`, then waits up to 60 s for in-flight changes and for `quiesce` BEFORE any header, and then runs the move to its end whatever the client does. If the connection drops in that window (WebKit's network process — the D30 shape), the client throws `UNAVAILABLE` with no `onOpen`; `reached` is false and `isStreamCutOff(err, false)` is false, so the screen says "The move could not be started: … Nothing was copied or changed." and goes back to the plan. Probe (deleted): `move` throwing `ApiClientError(0, UNAVAILABLE)` → exactly that alert; `moveStatus` asked 0 times. This is ledger line 272's point ("no false 'nothing changed'") for the part before headers. Direction: after any status-0 failure of the move request, ask `/libraries/move/status` (and `library.state`) before saying anything; or have the service send headers before it waits.
