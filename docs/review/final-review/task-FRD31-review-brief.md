## The finding
The project's owner imported a Zotero library of several thousand items with the built Mac app (a local folder, not encrypted). The import stopped; its report said "The import stopped with an error. What was imported so far is kept; you can undo it." — Created 81, Waiting for review 55, Merged 1, Skipped as duplicates 33, **Failed 213**, files copied 115 — and listed 213 identical lines: "zotero:U9FCJAKW: The item could not be imported." What was found (not proven on the owner's Mac — the owner has been asked for the disk's free room): **the disk holding the library filled up.** The Zotero database is copied into the library's work folder for the whole scan; the imported files then fill the disk; every item fails; at 200 unsaved journal lines the checkpoint fails too and the batch stops; stopping deletes the database copy, which frees the room in which the report is saved.

## Attack hardest
1. **Nothing lost, nothing twice, nothing false.** A batch stopped by a full disk and then resumed after room is freed: is every item imported exactly once (no duplicate source, no item silently dropped, no item recorded "failed" that a resume would have imported, no file half-copied left in the library or its work folder)? The item in hand when the disk filled: what is on disk of it (a source folder without its file? an audit entry? a write-ahead marker that recovery must settle)? Every library change is governed, audited and crash-safe through the marker (R26): does stopping in the middle of an item's store leave the project in a state that the next start refuses or repairs wrongly?
2. **The full disk at every point.** ENOSPC or EDQUOT thrown by: the copy of a file; the journal's append; the checkpoint; the batch record; the audit log; the index (SQLite: `SQLITE_FULL`, a failed journal file); the write-ahead marker; the Zotero database copy at the scan's start; the report at the end. Each: a stop with the right sentence, resumable — or something else? A disk that fills and is freed while the batch is paused. A QUOTA on a network share. `statfs` that cannot tell (Infinity) or lies (a cloud folder).
3. **The check before the start (a).** The size used: the dry run's (kept in memory only — a stale one from an earlier dry run of the same place after the folder changed; a dry run of another project or another source), else the source's own cheap total. Can the check REFUSE an import that would fit (linked files counted as copied; "leave the files where they are" chosen; duplicates that will be skipped; a resume of a batch already half copied) or PASS one that will not fit by far? The cost of the cheap total on a folder of 100,000 files or a ZIP with a lying central directory (bounded? cancellable?). The sentence: are both numbers what a researcher would recognise ("3.2 GB" against Finder's figure), and is it true when X is less than Y but X plus the margin is not ("would copy about 3 GB … only 3.2 GB free")?
4. **Margins.** 500 MB (or 10%) before the start, 200 MB before each item: a small import on a nearly full disk; a library on a small external disk; do the test seams (`bulkSpaceSeams`, honoured only when NODE_ENV is "test") leak into production?
5. **(c) `RecoveryPendingError`.** Is the batch stopped at the first refusal, with a sentence that points at something that EXISTS in the product ("Open the project's notices, settle it, then resume the import" — is there such a place)? Other refusals that are the batch's condition and still fail item by item: a project locked in the middle (`ProjectLockedError`), a library that became read-only, a policy that denies every item.
6. **Part 1's report.** The reasons shown: plain words, no path, no secret, no stack, no raw error text of the system (R96); grouped; counts add up to the failed total; an unknown error still says something useful ("an unexpected error (EIO)"?) — is the kind/code shown ever a leak? The service's log line: what it holds of the researcher's titles, names, paths. The screen: `UserText` for anything from the data, accessible structure (headings, lists), a group of 213 does not render 213 lines by default.
7. **The torn append (R393 c).** `repo/io.ts`: an append cut short by the disk is finished or undone — a crash between the two; another writer appending meanwhile; the audit log (hash chain) and the journal both.
8. **The owner's own path.** After this fix, would the owner's report have told them what happened and what to do? Follow it: the dry run, the start, the stop, the report, "Resume", and "Undo" of a batch stopped this way.
