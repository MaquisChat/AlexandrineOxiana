## NEEDS A RULING

**FR-335 — a pairing code stays `confirming` without a time limit.** Found: `auth.ts:299-317` marks the code `confirming` while the pairing is written; the write (`updateAppSettingStrict`) has no bound, and the screen's own countdown (`ExtensionPairing.tsx` countdown effect) calls the code "expired" at its expiry even while the service says `confirming`. A time limit alone needs a decision on what is true when it passes, because the write cannot be cancelled and may still land: (a) at the limit the status becomes `invalidated`/`not-saved` and a write that lands later is undone (the pairing removed again in the same file turn) — truthful, more than S; (b) at the limit the status says nothing new, and only the screen changes: on `confirming` it stops its countdown and says "The right code was typed. The pairing is being saved…", and after, say, 60 s more "The pairing is taking longer than it should to be saved. Reload this page in a moment to see whether the browser is in the list." — small, truthful, but no limit in the service. Recommendation: (b) now (UI, S), (a) only if the owner wants the service to give up.

**FR-370, FR-371 — addresses a lock cut from a capture queue.** The controller ruled at Task 63 that queues are not kept across a lock (an encrypted project's records leave memory at the lock, R30/R50). Keeping the cut list so that something reminds after the unlock means holding a locked project's addresses somewhere while it is locked. Options: (a) the app (the screens, in memory only, not storage) keeps the cut addresses per project for the session, and after the unlock the project's library view shows "A lock stopped a capture of N links in this project before they were tried. Show the links" with "Capture these again" — lost on reload or quit; the addresses are already in that page's memory today while the Capture screen is open; (b) at the lock the service writes the cut addresses into the project as a sealed, governed, audited record, and the unlock offers them back — survives everything, but a new record kind, a route and a screen: plainly larger than M. Recommendation: (a), with the sentence above, if the owner accepts the addresses staying in the app window's memory while the project is locked; otherwise leave as is.

**FR-393 — a lock (or crash) between the two store writes leaves the first try's lone file as an extra version.** `packages/library/src/transcript-store.ts:39-63` stores the WebVTT and the segments file as two governed changes. The controller's ruling at Task 62 (LEDGER after line 777) allows two fixes; both change something ruled: (a) one governed change that stores both files (a new plural `addDerivedAssets` in `repo/assets.ts`) — the lone file can no longer happen, but each transcription then audits ONE `store` entry for two assets instead of two (the header of `transcript-store.ts` and tests in `packages/library/src/transcription-jobs.test.ts` ~l.230-262 and the F-1 test hook the second `addDerivedAsset` call and assert `["process", "store", "store"]`); (b) the rerun removes the first try's lone file in the same governed change as its own pair — needs the first try's files to be found again (by job id, which R1-1 recorded and was reverted) and a removal of a derived asset, more than S. Recommendation: (a), if the owner accepts one audit entry per stored transcript.
