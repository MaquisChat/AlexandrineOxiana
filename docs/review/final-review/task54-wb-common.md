## How to review
- You cannot read every line. Spend your effort where a mistake costs most in your part (your dispatch names the places), read those paths end to end, and PROBE: a crash or thrown error half-way, two calls at once, a locked or encrypted project, a read-only library, hostile or odd input (control characters, bidi marks, very long strings, `..`, symbolic links, names differing only by case — a Mac's disk ignores case), a missing or wrong Origin, Host or token, an answer the screen does not expect.
- Seams between parts are where the per-task reviews saw least: for a request, open both the caller and the handler; for a file format, both the writer and every reader; for a rule, every place that should ask it.
- For each claim you make, have the evidence: file:line and the probe's output or the exact path through the code.
- Tests: where risky logic has no test that would fail if the behaviour were removed, say so.
- Severity: **Critical** = data loss or corruption, a privacy or security breach, a governance or audit bypass, a half-written change presented as real, a secret exposed. **Important** = wrong behaviour a researcher would meet, a contract mismatch between two parts, a ruling not met, risky logic untested, an accessibility failure that blocks keyboard or screen-reader use. **Minor** = the rest (at most ten, the most useful).
