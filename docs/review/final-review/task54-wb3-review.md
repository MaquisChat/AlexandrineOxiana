## Findings

### C1 — A participant's name in a file name is sent to OpenAlex on every import, under the default rules
`import/resolve.ts:464-481` (step 5) and `:483-491` (step 6); `lookup/openalex.ts:69-79`; reached from attach (`attach.ts:307`), Bulk Import (`bulk/run.ts:1351`) and watched folders (through attach).
For **any** file, of any type, whose name fits a built-in pattern (`Author - Year - Title`, `Author_Year_Title`, `Author (Year) Title`, `Word Year Words…`, `core/import/filename-patterns.ts`), the parsed title **and creator** are sent as an OpenAlex search; step 6 sends the best title known so far (e.g. a document's embedded Title) the same way. The only gate is `processing.metadata_lookup` containing `openalex`, which the default governance (and the IRB profile, which does not narrow it) allows. Nothing considers whether the project holds identifiable data, whether it pseudonymises file names, or whether the file is a recording or photo (for which a bibliographic title search is meaningless).
Probe (`resolve.probe-wb3`, deleted): `resolveItem` of `Gonzalez 2024 Interview about her eviction.m4a` (`audio/mp4`) with the project's policy = `DEFAULT_GOVERNANCE` (containsIdentifiable true, pseudonymizeFileNames true, encryption required) and `sensitive: true` requested
`https://api.openalex.org/works?search=Interview+about+her+eviction+Gonzalez&per-page=5`.
Breaks: SPEC §5.4 step 1 ("if identifiability rules apply, file names are pseudonymized on import") and the brief's first "must never" (a participant's identity leaving where the project's rules allow); `sensitive` only keeps the answer out of the disk cache. R14 exempts metadata services from the vendor declaration; it does not decide that identifying file names may be sent. No test asserts that a recording's or an identifiable project's file name stays on the device.
Direction: no title search (steps 5 and 6) for audio, video and image files at all; in a project whose store of identifiable data carries `pseudonymize-names`, no title search from a file name or embedded metadata (DOI/ISBN lookups can stay); a test that fails if such a request is made. **Needs the coordinator's ruling** on how far to narrow (I graded Critical because it is the default configuration and the data are names).

### I1 — Browser capture stores the page's address with its credentials and secret query
`capture/browser-capture.ts:181-210` (`identifiers.url` and `provenance.originalUrl` = `c.canonicalUrl || url.href`); `core/capture/platforms.ts:61-67` (`stripTracking` keeps every non-tracking parameter and the `user:password@`).
The extension sends the tab's `location.href` as is (`apps/browser-extension/src/content/index.ts:52`, `background.ts:141`); the route passes it through (`apps/library-service/src/routes/capture.ts:403`). For a web page (platform "other") on a signed-in site — the very case browser capture exists for (`access: "signed-in-session"`) — the address keeps `?access_token=…`, `sessionid=…`, a signed link's signature, or a user name and password. Probe (`browser-url.probe-wb3`, deleted): `url = https://ana:hunter2@portal.example.org/case/7?access_token=SECRETTOKEN&sessionid=SESS#frag` → stored `identifiers.url` and `provenance.originalUrl` both `https://ana:hunter2@portal.example.org/case/7?access_token=SECRETTOKEN&sessionid=SESS`, in source.json (plain in an unencrypted project), the change log, the index and every citation or export that prints the URL.
Breaks R41 C1 / R99 I8 (the snapshot's URLs lose their query; the HTML snapshot's do too, `html-strip.mjs:49-55`, but the page's own address is not cleaned) and the standing rule "no secret in an address, a log". The existing test (`service-support.test.ts:369-379`) puts the token only in `extracted.canonicalUrl`, never in `url`, so it cannot fail for this.
Direction: clean the stored address like the snapshot's (drop userinfo always; drop query parameters whose names are secret-like by the same word rule, or the whole query for non-platform pages, keeping the full address only where the researcher typed it); add a test with a token in `url`.

### Minor
- **M1** `extract/zip.ts:266-283`: the case-fold guard only compares whole entry paths. An archive with a file `notes` and a file `Notes/a.pdf` is accepted on Linux, but on a Mac's case-insensitive disk the `mkdir` of `Notes` fails with EEXIST and the outer catch refuses the **whole** archive as "could not be read" (fails closed, but every other file is lost with a misleading reason). Direction: fold directory prefixes into the same set and refuse only the later entry.
- **M2** `import/bulk/scan.ts:255-258` / `extract/zip.ts:221`: Bulk Import unpacks up to 2 GB per archive into `<Library>/.tmp` without the `beforeWrite` free-space check the restore uses; a large archive on a nearly full library disk fails mid-way (only that item; no data loss).
- **M3** `import/bulk/run.ts:849-853`: a resumed batch passes by every item with any journal line, `failed` included, so an item that failed for a passing reason (an unexpected error, `REASONS.failed`; an archive that could not be read for a moment) is never tried again by "Resume" — only by a new batch. The report says "resume the batch to continue" only for a stopped run. Worth a sentence in the report or a retry of `failed` lines on resume.
- **M4** `import/bulk/outside.ts:29-33`: `within` treats a sub-folder whose name begins with `..` (e.g. `..data/`) as outside the root, so its files need an approval they should not need (fails closed; the same shape R233 e fixed elsewhere).
- **M5** `import/watch.ts` (stability rule, `WATCH_STABILITY_MS = 2000`, `:133`): a file written by a program that pauses more than two seconds (a slow network copy, a recorder flushing in bursts) is imported half-written; under R207 (3) its completion is then only noted "changed" and never imported by itself. By design, but the guide should tell researchers to write into the folder by moving finished files in.
- **M6** `lookup/http.ts` + `import/resolve.ts:373-491`: one item can wait for up to 3 identifier lookups × 2 providers + 2 searches, each up to 4 attempts with 60 s deadlines and Retry-After up to 60 s; a hanging service stalls a Bulk Import (sequential) for many minutes per item. A per-item lookup budget would bound it.

## Checked and sound

- ZIP: `..`, absolute, drive-letter, backslash and NUL names and Unix/OS X symlink entries refuse the archive before anything is written; sizes checked as declared and again while inflating (never more than declared, per entry and in all); 100,000 entries; files `wx` 0600 in a 0700 folder; NFC + lower-case duplicate names refuse only the later entry; nested archives are not opened; the unpacked copies are removed after their items.
- Pause / suspend / cancel / crash of a batch: the pause takes effect between items after a checkpoint that writes the pending journal lines with the record in one governed change; a group of up to 32 new sources is stored with its journal lines in the same change; a crash between source and line is caught by the resume guard (HMAC of the item key in the source's provenance, `run.ts:2393-2406, 844-848`); a second resume at the same time is refused synchronously; a `running` record of no live process is shown as interrupted.
- The duplicate decision uses the live index plus in-batch keys and placeholders that stop matching once dropped; sources added during the batch count.
- Outside-the-folder files: real paths, approvals kept as HMACs only, honoured on resume.
- Watched folders: the per-folder gate holds one call in flight, a stuck call blocks the folder until it settles, and the name rule skips partial-download names (`.part`, `.crdownload`, `.download`, `.tmp`, `~$`, `.partial`, safe-save names).
- Snapshot stripping of platform JSON (secret-word keys, signed media keys, local paths, value-level query strip); the HTML snapshot runs in a bounded worker pool and loses every URL's query.
- MOBI header parsing bounds every offset and count.
