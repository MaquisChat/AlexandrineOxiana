## What is wrong (review: `/home/user/AlexandrineOxiana/.superpowers/sdd/PLAN/task54-wb4-review.md`, finding I3 — read it; and its check 4 on texts that can be false)
"Find and acquire": the researcher types a reference; the app finds the record and then looks for a free copy at several services; when one offers a file, the app downloads it and HOLDS it for the researcher's own check (a found file is never attached without that decision — do not touch that). In `packages/library/src/find/runner.ts` (about :2150–2206): each offered file is downloaded in turn; a download that fails for ANY reason (a time-out, a 429, a 503, the network — `FetchFileError`, or the `TimedOut` of `FIND_DOWNLOAD_TIMEOUT_MS`) is a debug line and the next offer is tried; when no offer gave a file, the entry is written `no-open-copy` with its reason dropped. `retry` (about :2400–2412) accepts a `no-open-copy` entry only with the reason `copy-some-unreachable`, so the row shows "No open copy" and offers no "Try again" (the screen's table: `packages/ui/src/screens/find/FindAcquire.test.tsx` about :2759). But a copy WAS found; it could not be fetched this time. A test (`find/runner.test.ts` about :3987–3998) pins exactly this wrong outcome for a timed-out download.
The same distinction already exists one step earlier: when the SERVICES that say whether a copy exists cannot be reached, the entry is not "no open copy" — it waits and is tried again by itself like an unreachable look-up, and if it still fails it says a free copy may still exist and offers "Try again" (Ruling R282 e; also R310, R296 d, R283 a — read them: `grep -n -E "Ruling R(282|310)\b" /home/user/AlexandrineOxiana/docs/handoff/LEDGER.md | cut -c1-6000`, and read how it is built: grep `copy-some-unreachable` in `packages/library/src/find`, `packages/shared/src`, `packages/ui/src`).

## What to build — mirror the unreachable-services case; do not invent a second mechanism
1. **Tell a passing failure from a final one, per offer.** Passing: a time-out, a network error, a connection reset, 408, 425, 429, 5xx. Final: 401/403/404/410 and other 4xx, a file that is not a PDF or not what its name says, too large, a refusal by the project's rules or by the fetcher's own safety rules (read `FetchFileError`'s codes and sort every one of them into the two groups in a small table in the code; an unknown error is passing).
2. **When at least one offer failed for a passing reason and no file was obtained:** the entry is NOT `no-open-copy` with no reason. It gets a reason of its own, `copy-not-downloaded` (beside `copy-some-unreachable`, in the same shared list of reasons), the links stay on the entry as now, and it behaves exactly as `copy-some-unreachable` behaves: it is tried again by itself on the same schedule and the same number of times (find how many and when for the unreachable services and use the same code path), and after that it rests as "no-open-copy / copy-not-downloaded" with "Try again" offered — `retry` accepts it. Its sentence on the row, exactly: "A free copy was found, but it could not be downloaded just now. Try again later, or open one of the links." (beside the existing sentence for unreachable services; use the same place and the same control).
3. **When every offer failed finally:** as today — `no-open-copy`, the links kept; nothing to try again by itself.
4. **A download refused because the researcher cancelled, the entry was removed, or the project locked:** unchanged.
5. The screen: the row shows the new sentence and "Try again" for the new reason (the row's table of states is in `FindAcquire.tsx` / `FindEntryRow.tsx` — find it); nothing else on the screen changes. The shared texts live where the feature's other texts live (`packages/shared/src/api/find.ts`).
