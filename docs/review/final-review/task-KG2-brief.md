### FR-727 — what counts as a missing linked file (R503 f)
Today only a path where nothing is counts as missing; a dangling symbolic link, a folder where a file is recorded, and a file that cannot be read for want of permission all count as present — "in your library" in Find and acquire, and not in the Missing files list — though nothing can be read.
Ruled: a recorded linked file is MISSING when (1) nothing is at its path (as today), (2) the path is a dangling symbolic link, (3) a folder is where a file is recorded. A file that is there but cannot be read for want of permission is NOT "missing": it keeps today's answer, unless the app ALREADY has a researcher-visible state that says "cannot be read" for a source's file — look, and report what you find; invent no new state. The Missing files list and Find and acquire change TOGETHER, by the one shared rule (change the rule, not its callers; the callers' tests then show both). Mind: the rule uses `lstat` today (it does not follow links) — decide by reading what following a link costs (a link to a file on an unplugged drive IS a dangling link and IS missing; a link to a file that is there is present); a path that escapes the library root is refused as it is today. Does reconnecting a folder ("Missing files" → reconnect) still work for each new missing kind — and what does it do to a dangling link at the old path (it must never delete a person's link without saying; read what reconnect writes)? If reconnecting needs a choice, that is a NEEDS A RULING — the judging alone may still be built.
Tests first, at the rule (`linked-file` tests), at the Missing files list, and in `packages/library/src/find/runner.linked-missing.test.ts` (each new kind rests `record-complete` with reason `linked-file-missing`, and NOTHING is asked or fetched: assert zero calls on the stand-in sources and the fetcher, as the existing tests do).

### FR-728 — a resting entry is judged again when its source has a file by another way (R503 g)
An entry of Find and acquire that rests for want of a copy (for instance after "Not this file", or "No open copy") keeps saying so when its source later has a file some other way (a linked file's drive returns; a file is attached by hand in the library).
Ruled: at the queue's opening — the one pass that R483 a added (find it in `runner.ts`; read its tests) — an entry that rests for want of a copy and whose source now has an original that can be reached (stored, or linked and reachable by the rule above) comes to rest "in your library". RESTING STATES ONLY: the pass never fetches, never asks a source, never wakes an entry, never touches an entry being worked on or one with the researcher's pick set (R483's rules hold; read them). Decide by reading WHICH resting states mean "for want of a copy" (list them in your report with your reason for each; `not-this-file` is one; an entry that rests for a reason the researcher must act on in another way — a rule that forbids, a key that is missing — is NOT). One line written once (how the existing pass guards "once").
