# Review: FR-765 / FR-764 / FR-759 (branch `fr-765-nothing-after-stop`, b23a81b..bb9e1b8)

**Verdict: Ready with fixes.** I found no Critical or Important fault. The builder is right on every point I checked: what they say is mended is mended, each new test fails without its mend, and no test loosened. The fixes below are Minor, and each can be a follow-up.

## Findings

**Critical:** none. **Important:** none.

**Minor**
1. **A stopped caller still uses up a pacing slot.** `lookup/http.ts:699-709` (`throttle`): the queued turn still sleeps and advances `nextSlot` after its caller has gone. A probe (arXiv, one request per 3 s) showed project B waiting 6 s instead of 3 s behind one stopped waiter. On hosts with no concurrency limit, every stopped waiter costs one gap. Pacing is never skipped (safe), and this is not a regression: before the change the stopped run actually sent those requests. Smallest fix: before sleeping, a turn whose caller has already stopped skips the sleep and does not advance `nextSlot`.
2. **The FR-759 purge, and the existing lock purge, drop everyone's sensitive answers.** `routes/sources.ts:363`: `purgeSensitive()` clears every sensitive entry, including those of another encrypted project that is still unlocked. Only a repeat lookup is lost, never correctness. This is the same coarse rule as R600 I2 and the lock route, so I accept it as is.
3. **Leftover timer.** `import/zotero-web.ts:359,374`: after a stop, the default sleep's `setTimeout` (up to 120 s, `MAX_WAIT_MS`) is neither cleared nor unref'd. It sends nothing. When it fires it only resolves a promise nobody waits on, so nothing reaches a closed library. It can keep a short-lived process (such as the command-line tool) alive for up to 2 min. Fix: clear the timer on abort (pass the signal to the default sleep) or `unref()` it.
4. **Misleading debug note.** A stopped run's free-copy lookup writes the debug note "free copy via openalex skipped: it could not be reached" (seen in my probe). It is a debug note only, never shown on screen, and nothing else is written.

The download keeps its own stop (FR-757). I found no call outside a context. A timed-out lookup (`TimedOut`) is still not aborted. That is pre-existing and outside this rule.

Every wait is cut by the caller's stop: the slot, the place, the throttle, and the Retry-After and back-off waits. The `keyReady` wait is not cut, but nothing is sent after it without the check.

- **F.** The lock route calls `stop(projectId)` only, which aborts that project's run. Attach, "Look up again", imports and other projects carry no signal and are untouched. A move or a close calls `stopAll`, which stops every run.
