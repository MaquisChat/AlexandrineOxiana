## What is wrong (review: `/home/user/AlexandrineOxiana/.superpowers/sdd/PLAN/task54-wb2-review.md`, finding I1 — read it)
The project's rule (its specification): "All paths stored inside the library are relative to the library root. No absolute paths are stored in the database, `source.json`, or any other library file" — the only exception is a file LINKED in place from outside the library, whose own path is kept in its asset record. The library is a folder the researcher can move to another disk or computer.
The media worker (audio and video proxies, text recognition, transcription) is given jobs; each pending job is recorded in `<Project>/jobs/journal.jsonl` so that it can be resumed after a crash (`packages/library/src/worker-client.ts` about :423–447, `StoredJob { input, output }`; `job-journal.ts`). The callers pass ABSOLUTE paths — `import/proxies.ts` about :308/:320 (`join(root, asset.path)` or a linked file's `absolutePath`; the output `join(root, ".tmp", …)`), `import/ocr.ts` about :240–245, `transcription-jobs.ts` about :66–68/:101–103 — and the journal stores them as given. In a project that is not encrypted those lines are plain text; they name the researcher's user folder, and after the library is moved or copied they name the previous place (and a resume then looks for the file where it no longer is).

## What to build
1. **The journal stores library-relative paths.** A stored job's input and output are kept relative to the library's root (POSIX separators, no leading slash, no `..`), and turned into absolute paths against the CURRENT root when the job is submitted or resumed. An input that is a file linked in place from outside the library is not stored as a path at all: the job stores which asset it is (the source and asset ids — read what the callers know) and the path is read from the asset's own record when the job runs (the one place the specification allows it). If a caller hands in a path that is neither inside the library nor a linked asset's, that is a programming error: refuse it with an error that names no path, and test it.
2. **Old lines still resume.** A journal written before this change holds absolute paths. Reading such a line: a path inside the current library root is used as it is (and written back relative when the line is next rewritten/compacted — say when that is); a path that is NOT inside the current root (the library was moved) is re-derived from the job's asset when the job record allows it (transcription already recomputes its input on resume, `extras.input` — read it), and otherwise the job fails as it fails today for a missing input, with today's sentence. Nothing throws on an old line.
3. **Nothing else changes:** the worker still receives absolute paths (its protocol is unchanged); encrypted projects seal the lines as now; the journal's format stays one JSON line per record (add a field or reuse the existing ones — keep it readable by the code on the base commit if you can, and say whether it is).
4. Grep the rest of the library's files written at run time for other absolute paths while you are there (`grep -rn "absolutePath\|\.root\b" packages/library/src --include=*.ts | grep -v test` is a start; the batch records, the Find queue, the watch register, the device notices are NOT in the library folder or were checked by another review — only report what you find, change nothing else).

## Tests first (each seen to fail first)
