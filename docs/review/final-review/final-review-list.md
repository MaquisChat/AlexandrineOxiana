# Final review list - every point the decision log deferred

Compiled from `docs/handoff/LEDGER.md` (read at 1,694 lines; the last ruling is R360) and `docs/PLAN.md`, for Task 54 (the final review). Nothing in the repository was changed. Each item gives the log's own point in one or two sentences, quoting its wording where it could be quoted; where a ledger line holds several points separated by semicolons or by labels (N1, M5, ...) they are separate items.

**How to read a bullet:** `- **FR-nnn** [class] point (R<n>~, task, LEDGER:<line>)`. `R<n>~` is the nearest ruling number cited earlier on that ledger line, not necessarily the ruling that deferred the point; where none is cited, only the task and the line are given. `PLAN:<line>` is a line of `docs/PLAN.md`. Classes: `code` a change someone could make; `test` a missing or weak test; `wording` a loose or untrue sentence; `decision` needs the owner or the coordinator; `mac` only a real Mac, browser, library or publisher can show it; `superseded?` the log or the plan later says it was fixed, merged or withdrawn (the original class is kept in the bullet). Classes of the 345 items taken from the older "minor (deferred)" lines were assigned from keywords in their text and are only a first sorting; areas were assigned from the task number.

- **FR-711** (R454; group B, with FR-686) — the local service has no last handler for an uncaught error or an unhandled rejection (`apps/library-service/src`): one such error ends the process, and the app's screens then fail one by one with no word of why. To decide with the log file (decision 26): write the error where it can be found, and whether the desktop shell starts the service again.
- **FR-712** (R456's verification; group C) — the desktop scenario's check that every process of the run keeps its home and XDG folders in the run's folder (`apps/desktop/e2e/lifetime.ts` `processEnvProblems`, about :147–150) can catch a process in the act of ending — its environment already unreadable, not yet a zombie — and report "its environment cannot be read" (seen once, verification FR5, 18 November). It should look again a moment later (gone or a zombie by then: no problem) before reporting; a test with injected readers.
- **FR-713** (group C) — `apps/browser-extension/src/find.test.ts` about :625, "a tab whose file stops arriving: the wait for a piece ends…": ran past the default 5-second limit once on GitHub (CI run 273 on `main`, the Python 3.12 job) while the identical tree passed twice elsewhere; it moves 3 MB through base64 in pieces. To prove (run it with the processor throttled) and then give it its own limit or a smaller file.
- **FR-714** (R457; group B) — on a Mac, listing and removing the sign-in window's data stores at start-up, at quit and at sign-out has no time limit (`apps/desktop/src-tauri/src/library_window.rs`, the Mac `remove_data_stores`, about :2197): if WebKit never answered, the app would wait for ever before its service starts. A limit, and what the app says and allows when the store could not be emptied.
- **FR-715** (R458; group B, for the owner) — on a Mac, when a page cannot be loaded in the sign-in window (no network, a wrong address, a certificate error, the site down) the window stays blank, with no message; on Linux the web view shows its own error page. Neither `wry` nor `tauri` reports a failed load, so saying something needs Mac-only code (a navigation delegate's failure methods) or a time limit on the first page ("Nothing has loaded. Check the address in Settings, or try again.").
- **FR-716** (R459; group B) — the check and the Linux build on Ubuntu 26.04: GitHub's `ubuntu-latest` became 26.04 between 18 and 23 November 2026; `webkit2gtk-driver` is `webkitgtk-webdriver` there, and the web view's version, the WebDriver and the launch check are untried on it. `ci.yml` is pinned to `ubuntu-24.04` meanwhile; the Mac workflow's two Linux jobs (plan, browser extension) still say `ubuntu-latest` (`apps/desktop/scripts/build-macos.test.mjs` :520 names it).
- **FR-717** (R461; group B) — a project recheck left running by leaving the library is shown again on return only from its next event (until then the button is enabled); closing the gap needs the service to list the rechecks that are running (`packages/ui/src/components/RecheckProject.tsx`; the 34d review said the same).
- **FR-718** (R464; group B) — a pairing code's save has no time limit in the service (`apps/library-service/src/auth.ts` about :299–317): the screen now says the pairing is being saved and reads the list again; a service that gives up at a limit must also take back a pairing whose write lands late.
- **FR-719** (R464; group B, for the owner) — a capture queue that survives a lock: the links are kept sealed in the project from the moment they are queued and offered again after the unlock. Today a lock cuts the queue and only the count of the links cut is remembered (what belongs to an encrypted project leaves memory at a lock).
- **FR-720** (R465; group B) — the library-wide warning that the watched folders were not started (the computer's list unreadable when the library was opened) does not clear by itself: when a later read of the list succeeds, the service could start every project's watches again and take the warning away (`apps/library-service/src/state.ts` about :892, `routes/watched-folders.ts`); it also sits among the integrity warnings, which is a mix of kinds.
- **FR-721** (R473; group B) — the libraries list (`packages/library/src/library.ts` `registerLibrary`) is written by the service AND by the command line (`apps/cli/src/commands/library.ts`, `session.ts`): two processes can race — one registration lost, or one rename failing over a damaged list. Within a process the writer now re-reads and merges; across processes it needs a lock file or the same merge with a retry.

- **FR-722** (listed 23 November 2026, Ruling R476 e; Minor; not built): the media worker cannot read the Mac's keychain. On a network whose own inspecting proxy re-signs secure connections (some universities, some security programs) and whose authority is installed only in the keychain, a tool download is refused even after R476's fix — with the sentence that says a VPN, a security program or an inspecting network can cause it. A way to honour the keychain (for instance the `truststore` package) would be a new dependency and a decision of its own.

- **FR-723** (listed 23 November 2026, Ruling R479 c; Minor; not built): when the app undoes a change it had not finished, a file that change wrote by copying (a stored original) or inside a folder the change itself created has no hash in the transaction's marker. If someone changed such a file by hand before the library was opened again, the hand change is undone without the warning the other named files now get ("…the outside change to that file was not kept").
- **FR-724** (listed 23 November 2026, Ruling R479 c; Minor; not built): in the notes of an export made from a restored copy, a file of the backup that has the same bytes as one the project destroyed before the backup was made is described as destroyed by the project's own retention. That is true of the bytes; it is not that file's own history.
