## Findings

### Minor
1. **The emptying has no bound after WebKit is started** — `library_window.rs:2203-2218` (pre-existing, not touched by the fix). `start_webkit` is bounded (10 s), but `block_on(fetch_data_store_identifiers())` and `remove_data_store` wait on WebKit's callbacks with no timeout. If WebKit starts but never answers, `at_start` blocks the launch thread for ever: no service, no main window, no failure dialog. R457 (b) speaks of "its existing bound"; there is none for this part. The report to the owner should say so and not claim a bound. Direction: if this is ever seen, put a timeout on the `block_on`, or leave it as is and say plainly that there is no bound.
2. **A failed emptying leaves the old store's data on disk** — `renew_closed` :1804-1811 (pre-existing). When `start_webkit` or the removal fails, a new store id is still made and written. The old store, which may still hold a session, then sits unused on disk until a later emptying succeeds (that emptying lists every identifier and removes it too). No window can reach it, and `at_start`'s `false` is dropped (`lib.rs:154`) without even a log line. This is acceptable under R457 (b), but the report should say it. Direction: an `eprintln!` when `at_start` returns false would make a Mac failure visible in the launch check's log.
3. **No test holds the guard.** The change is macOS-only and touches WebKit, so no Linux test can fail without it. The Mac launch check is its only proof, as R457 (c) itself says. Noted, not a defect.

## Checked and sound
- **Threads.** The Mac `remove_data_stores` is reached only through `TauriHost::remove_data_stores` (:2101), which returns false on the main thread before calling it. Its callers are `renew_closed`, which is called by `at_start`, `at_quit` and `sign_out`. `at_start` runs on the `launch` thread (spawned in `setup`, lib.rs:403). `at_quit` runs on a thread spawned from `ExitRequested` while the loop is held open with `prevent_exit`. `sign_out` runs on a `detached` std thread. None of them is the main thread, and none is a runtime worker, so `block_on` is legal there. A sign-out pressed early, or a quit while `at_start` is still running, posts from a second thread. Both may post `defaultDataStore`, which is harmless and idempotent. `STARTED` is set only on success. A late closure after a timeout sends to a dropped receiver (`let _ =`), which is fine.
- **The event loop is running when `at_start` posts.** Tauri 2 calls `setup` from `RuntimeRunEvent::Ready` inside `run_return` (app.rs:1442), and `launch` is spawned from there. `run_on_main_thread` is `send_user_message(Message::Task)`, which is queued and runs on the next turn of the loop. A second instance exits in the single-instance plugin before `setup`. `fail()` blocks only the launch thread. Every `fail` before `at_start` exits before any store is touched. No start path has the main thread blocked while `at_start` waits.
- **What follows from `false`: a sign-in window cannot open on an un-emptied store.** `renew_closed` makes a new store id whatever `removed` says (:1806-1809). `open` takes `device.store` (:1502) and builds the window with `data_store_identifier(store)` (:2030 → :2172). So after a failed emptying the window opens on a fresh, never-used identifier. If `new_store_id()` fails, `device` stays `None` and `open` refuses (:1502). If the device file cannot be written, the new id is still used in memory.
- **The call matches the crate.** `pub unsafe fn defaultDataStore(mtm: MainThreadMarker) -> Retained<WKWebsiteDataStore>` (method family none, so the result is +0 autoreleased and retained by `Retained`). The call is inside `unsafe`, `mtm` comes from `MainThreadMarker::new()` (exists, returns `Option`, root re-export `objc2::MainThreadMarker`), and `_store` is dropped at the end of the closure on the main thread. The `WKWebsiteDataStore` feature gates the class (generated/mod.rs :584, :2069) and pulls in its objc2-foundation features. `objc2-foundation` is a non-optional dependency. wry enables the same features (`std`, `WKWebsiteDataStore`) on the same versions, so the comment in Cargo.toml is true. `Duration` is already imported (:58). I expect it to compile.
- **No side effect on the default store.** The main window sets no identifier and is not incognito, so wry gives it `defaultDataStore` (wry mod.rs:286). Obtaining the default store early creates nothing the main window would not create moments later. It does not change where the main window keeps its data. `fetchAllDataStoreIdentifiers` lists identifier stores only, so the default store is neither listed nor removed. The "Stay signed in: off" promise concerns the sign-in window's identifier stores and is unaffected.
- **The comment is true**, except where it says "its answer went to a main run loop that did not exist", which is the ruling's diagnosis and only the Mac run can confirm it. "Never on the main thread" is true thanks to the host's guard.
- **Nothing else at start-up calls WebKit before the main window.** Up to the main window's `build()`, `launch` makes only folder, token, service and dialog calls (the dialog is NSAlert, not WebKit). `start_webkit` is called right after `empty_inbox`.
