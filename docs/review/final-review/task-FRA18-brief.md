## What is wrong (review: `/home/user/AlexandrineOxiana/.superpowers/sdd/PLAN/task54-wb6-review.md`, finding I1 — read it, with its probe; and `task54-wb1-review.md`, check 2 and M2)
Each project has a rules file, `governance.yaml`. The policy engine reads it strictly (`parseGovernance` in `packages/core/src/governance/schema.ts`): an unknown key, a wrong type or a bad value makes the file unreadable, and then EVERY capture, import, change and export in the project is refused ("governance fails closed"). That is right. But nothing tells the researcher:
- the service's `GET` for the rules (`apps/library-service/src/routes/governance.ts` about :71–84) swallows the parse failure and answers `violations: []`;
- the Governance screen (`packages/ui/src/screens/GovernanceSettings.tsx` about :124–157, :289–293; `screens/governanceModel.ts` about :179–186) reads the file with its own lenient reader, so a file the engine cannot read is shown as a normal set of rules, with no warning;
- the Capture screen (`packages/ui/src/api/capture.ts` about :133–145, `readable: false`) and the Import screens (`api/import.ts` about :315–324) fall back to strict rules without saying why.
So the researcher meets a wall of refusals beside a screen that says the rules are fine. Ruling R58 (read it: `grep -n -E "Ruling R58\b|^R58\b"` in the ledger and its index) asks that problems found when the rules are loaded reach the screen. Besides the fatal case there are NON-fatal notes: `parseGovernanceWithWarnings` (same file) returns warnings (for example "consent.defaultLegalBasis.manual_upload: ignored" — a legal basis written in an old form is not used), and nothing outside core calls it.

## What to build
1. **The service says it.** The rules' `GET` answers, besides what it answers now: `readable: boolean` and, when the engine cannot read the file, `issues: string[]` (the engine's own messages, in plain language, each naming the key and what is wrong — no file-system path, no stack; read what `parseGovernance` throws and turn it into one line per problem), and always `warnings: string[]` (from `parseGovernanceWithWarnings`; empty when none). Add the fields to the shared type the screen uses (`packages/shared`), typed so the screen cannot ignore them by accident (required fields). The `PUT`/save answer carries the same fields for the text just saved. Nothing else of the route changes; a project that is locked or a library that is read-only answers as now.
2. **The Governance screen says it.** When `readable` is false: an alert at the top of the screen (`role="alert"`, the existing warning style — find the class the screen already uses), exactly: "The app cannot read this project's rules. Until they are corrected it refuses every capture, import, change and export in this project." followed by the issues as a list (each through `UserText`). The cards below still show what the lenient reader shows (so the researcher can correct it), and the YAML text stays editable; "Save changes" works when the corrected text is readable. When `warnings` is not empty (and the rules are readable): a note (not an alert), "The rules were read, with these notes:" and the list. Both are re-read after a save and disappear when the cause is gone. Focus is not moved by the alert.
3. **The Capture and Import screens say why.** Where each learns that the rules are unreadable (`readable: false` in its policy answer — read how each gets it; if the import's does not carry it, add it the same way), it shows, in the place where it shows its other refusals, exactly: "This project's rules cannot be read, so nothing can be captured here. Correct them on the Governance screen." (Capture) and "This project's rules cannot be read, so nothing can be imported here. Correct them on the Governance screen." (Import — the wizard's first step and the drop zone on the Library screen if it has one that reads the policy; say what you found). The controls stay as they are today (strict / off).
4. Texts live in `packages/shared` beside the screens' other shared texts if the service or two screens use them; otherwise beside the screen.
