## The mechanism (orientation; read the code)
Every change to a library runs in a transaction (`packages/library/src/repo/txn.ts`). Before it acts it records marker lines — created / replaced / append / dir / trashed — so that a change interrupted by a crash is undone when the library is next opened (`undoEntries`: in reverse, best effort; the same marker may be undone again at a later opening — "a step already undone is never undone again", R493; steps under a put-back folder are skipped, R503 b). A change that cannot be completely undone stays in the list of interrupted changes (`ok = false` → "rollback-incomplete"). Before rolling back, files the change named that are neither as the change left them nor as they were before are found and a warning is recorded (kind `changed-outside-before-rollback`, Rulings R473 I1, R479 a, R484: `grep -n -E "Ruling R(473|479|484|491|493|495)\b" /home/user/AlexandrineOxiana/docs/handoff/LEDGER.md | cut -c1-9000` — read all six). Tests to build beside: `packages/library/src/repo/rollback-rerun.test.ts` (the enumeration of sequences), `rollback-own-writes.test.ts`, and the tests of `changedSinceMarker`.

## The two gaps
- **FR-735** (Important as a remedy, rare): when the undo must put back a stored original that the change trashed, and someone has meanwhile put another file BY HAND at that original's path, the app cannot put the original back. Since R491 it keeps the change in the list of interrupted changes and keeps the trashed original (before, the original was deleted) — safe, but stuck: the researcher cannot resolve it. And the undo of a "created" file removes whatever is at the path, even if a person replaced the change's file by hand.
- **FR-723** (Minor): a file the change wrote BY COPYING (a stored original) or inside a folder the change itself created has NO hash in the marker (the hash of a streamed copy is known only after the copy). So a hand change to such a file before the reopening is undone without the warning the other named files get.

## Ruled (R503 c) — build exactly this
1. **Completion lines.** For a file written by copying, and for a file written inside a folder the change created, the marker gains a line written AFTER the write is complete (and durable in the way the marker's other lines are) that carries the file's hash (and what else the existing lines carry for a "created" file). Old markers (without such lines) must be undone exactly as today: read how the marker's reader treats unknown or absent lines, and how a marker written by THIS code is read by the OLDER build (the owner's Mac build 10 may open a library whose last change crashed under a newer build, and the reverse: say in your report what the older reader does with a line it does not know — if it refuses the whole marker, that is a finding: STOP and report before choosing a format; the line must then be shaped so that the older reader ignores it or still undoes safely).
2. **The undo of a created file removes only the change's own bytes.**
   - No completion line for it: the file is the change's own half-written file — removed, as today.
   - A completion line whose hash the file at the path still has: the change's own bytes — removed, as today.
   - A completion line and the file's bytes DIFFER (a person changed or replaced it): the file is NOT deleted. It is MOVED ASIDE — into the library's own trash, the place the app already keeps what it removed (find how `tx.trash`/the trash folder names things and how the Trash screen lists them: the moved file must be findable there by the researcher, under a name that says what it was) — the step counts as undone, and a warning is recorded (below).
   - A file whose hash cannot be read (permission, I/O): not deleted, not moved; the undo is incomplete (`ok = false`), as R503 b rules for "could not look".
3. **A trashed original whose path is occupied is put back.** Today (R491 C a): occupied → `ok = false`, the kept copy stays. Now: if what occupies the path is the change's own bytes (its own later created/replaced line: `ownBytesAt`, extended to the completion lines) it is removed as the undo of that line already does; if it is anything else, it is moved aside in the same way as in point 2, the original is put back, and the warning is recorded. If the moving aside itself fails: nothing is deleted, `ok = false`.
4. **Nothing a person put there is ever deleted by a roll-back** — the property your tests enumerate: extend `rollback-rerun.test.ts`'s enumeration (or a new enumeration beside it) so that EVERY sequence of marker lines it generates is run with a hand-put file at each named path, at each point (before the first undo, between two undos of the same marker), and assert for every case: the hand-put bytes exist afterwards, at the path or in the trash, exactly once and unchanged; the library's own earlier state is back, or the undo is incomplete and every copy the app kept is still there; a second undo of the same marker changes nothing more (R493's rule, including for the files moved aside: a second run must not move the put-back original aside as if it were a hand-put file!). That last parenthesis is the trap this design walks toward: after the first undo puts the original back at the path, the path is "occupied" by the ORIGINAL; the second undo must recognise it as put back (the kept copy is gone; the `done` rule) and not move it. Prove it in the enumeration.
5. **FR-723's warning.** With completion lines, a copied file and a file in a created folder can now be judged by `changedSinceMarker` like the other named files: a hand change before the reopening raises the existing warning kind (`changed-outside-before-rollback`) — read exactly what that kind says today (R479 a's sentence) and whether it is true when the file was MOVED ASIDE and kept (the existing sentence says the outside change "was not kept": for a file moved to the trash that is no longer true). Propose the exact words in your report (they are judged by the review and the coordinator); mark it clearly. This is the only new sentence of your task.
