## The mechanism you are working in (find it by reading; this is orientation, not a substitute)
Every change to a library runs in a transaction (`packages/library/src/repo/txn.ts` and its callers). Before acting, the transaction records marker lines — created / replaced / append / dir / trashed — so that a change interrupted by a crash can be undone when the library is next opened (`undoEntries` undoes the lines in reverse, best effort; the same marker may be undone again at a later opening, so "a step already undone is never undone again", Ruling R493). A change that cannot be completely undone stays in the list of interrupted changes. ## The items

### FR-738 — the most serious listed gap (Important when it happens)
The undo refuses, as "its audit log could not be checked", any unfinished change that both ADDED to the end of a file and REWROTE that same file. One change of the app does that: Find and acquire's queue file, when a torn last line left by a crash is cut and a new line is added in one step (`packages/library/src/find/` — find the queue's append and its repair of a torn last line). If the app crashes a second time during exactly that step, the unfinished change is tried again at every opening of the library and refused each time; it cannot be resolved from the list of interrupted changes; the project stays blocked.
Ruled (R503 a) — build exactly this:
1. The queue's repair of a torn last line and the adding of the new line become TWO governed changes: first the cut (a rewrite), complete and committed; then the append. Each alone is a change the undo already handles. Prove by a test at the queue's level that crashes (use the existing crash seams of the tests — find how `rollback-rerun.test.ts` and the Find tests simulate a crash) at each step of the new sequence and reopens: the queue file is whole (the torn line gone or still there, never half), the entry is there or not, the change is undone or complete, the project opens. First write the test that reproduces the blocked state on the old code (two crashes; the reopening refuses) and see it fail.
2. A transaction REFUSES, before anything is written by the offending step, a change that would both add to the end of a file and rewrite that same file (either order): a programming error (a thrown error with a plain message for developers, as the transaction's other misuse errors are), with a unit test for each order. The undo's own end-of-file check is NOT loosened. Then find out whether any OTHER change of the app does the combination: grep the callers, and run the test files of every caller you find that both appends and rewrites (the coordinator's full verification is the net behind you, but say in your report which callers you checked and how).
3. Do not build a way to "unblock" a project already in that state: none exists outside a test. Say in your report what a researcher in that state would see after your change (still blocked or not), truthfully.
