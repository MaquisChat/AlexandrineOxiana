# 0005. Governance checkpoint

- **Status:** Accepted
- **Date:** 2026-11-09

## Context

The library holds material governed by IRB, GDPR, HIPAA and funder rules. Every action (capture, process, store, export, move, sync, ...) must pass one checkpoint so that rules are enforced in one place and cannot be bypassed by a new code path (spec 6.1, 6.3).

## Decision

- **Single entry point.** `evaluate(cfg, req)` is called before every action. It returns `allow`, `deny` with a reason, or `allow_with_conditions`; every variant carries `warnings`.
- **Strictest wins first.** `evaluate` computes `effectivePolicy(cfg).policy` and decides against that, so a project cannot be looser than its profiles. A profile violation does not deny by itself; it becomes a warning ("Governance setting <control> is stricter than configured because <profile> requires it").
- **Fail closed, never throw.** The whole evaluation is wrapped. A malformed config (shape is checked up front), a missing request payload, an unknown action or an unparseable date yields `deny` with `Policy could not be evaluated: <message>`.
- **Conditions, not silent changes.** When an action is allowed only if the caller does something (encrypt, pseudonymize file names, coarsen or strip location, export de-identified only), the decision lists those conditions in a fixed order (encrypt, pseudonymize-names, location, deidentified-only) and is `allow` only when there are none. Conditions are cumulative. The caller must apply them; the engine does not.
- **Residency.** A move needs the destination in the effective `residency.allowed`. For `cloud_folder` the folder must also be in `approvedCloudFolders` under HIPAA, or whenever that list is non-empty; with no HIPAA and an empty list any folder is allowed. HIPAA already removes `cloud_folder` from `allowed` when no folder is approved.
- **Processing.** The provider must be in the op's list, including `local`: a project may forbid even on-device processing.
- **Dates.** Protocol dates are calendar dates, inclusive, evaluated in the researcher's time zone (`tz`, an IANA name, default UTC; an invalid zone denies). Capture is allowed from `approvedFrom` through `expires` inclusive; a date with a time uses its UTC date part. Within 30 calendar days of expiry the decision carries a warning ("expires today", "in 1 day", "in N days").
- **Request and policy validation.** Request payloads and the effective policy's scalar fields are type-checked before the rules run; anything malformed denies.
- **Backup** (R125). A backup is a full copy of a project written to `<Library>/Backups/`, which is where the library itself lives. The request lists every kind of storage that folder may be on: its path and its real path, classified as for a move. When a kind cannot be determined, every plausible kind is listed (`uncertain`). Each one must pass the move's residency rule (the kind is in `residency.allowed`; a cloud folder is on the approved list where one is needed). `encryption.atRest: required` adds an `encrypt` condition. An unencrypted project cannot honour it, so the caller refuses the backup and no unsealed backup is ever made. No other control takes part, and a backup has no governance section of its own. The `store` decision does not check residency, so the project's own data is not checked against these rules where the library already is: only a move and a backup are. A governance edit that excludes the library's current place is accepted, and from then on only backups are refused.
- **Restore** (Task 50b). A restore makes a backup a new project of a library. The request (`action: 'restore'`, `restore.destinations`) lists every kind of storage the library's folder may be on, classified as for a backup. The rule is the backup's rule, shared in the engine: each kind must pass the residency rule, and `encryption.atRest: required` adds an `encrypt` condition. The caller refuses when the project in the backup is not encrypted, so nothing comes back unencrypted under such rules. No other control takes part. The caller asks this of two policies, and both must allow it (the strictest wins, as everywhere else):
  - the `governance.yaml` the backup carries, which becomes the new project's (`restore.rules: 'backup'`, the default);
  - the governance the project the backup was made from has now, when that project is in the library (`restore.rules: 'original'`). `rules` changes only the words of a refusal, so the reason says whose rules refused.

  A backup of a project that is not in the library is decided by its own rules alone. Three consequences are accepted (R179). A backup made before the original's rules were tightened cannot be restored into a place the rules now exclude. A backup whose own, older rules exclude the library's present place cannot be restored there either, although the original's current rules allow it. And no backup of a project is restored into the library while that project's governance file cannot be read. Each of these refusals says which rule refuses and what can be done (restore into another library; change or repair the original's rules). The copy always carries the backup's rules, never the original's later changes.
- **Sync** is denied in Phase 1; `view`, `share` and `delete` are allowed and will be refined later.

## Consequences

- Every action added later must be a `PolicyAction` with a rule here, otherwise it is denied as unknown.
- The checkpoint is pure and synchronous, so it is cheap to call and simple to test, but it only decides: recording the decision in the audit log is the caller's job.
- The caller must pass the researcher's time zone; if it does not, the date rules use UTC and may differ by up to a day from the researcher's calendar.
- The project name in the move reason is the request's `projectId` until the request carries a name.
- The repository (`packages/library/src/repo/mutate.ts`) audits every allow and deny decision for an existing project. `createProject` decides before the project, and so its audit log, exists. An allow is recorded as the first event of the new log. A refusal is a deny from `evaluate`, or a governance rule the project would break, such as encryption at rest required for an unencrypted project. It is recorded in the library's own audit log, `<Library>/audit/NNNN.jsonl` (Task 50), with who, the name asked for, whether it was to be encrypted and the rule's reason; never the passphrase. The library folder is the narrowest place that survives a restart and travels with the library. If the log cannot be written, the refusal still stands and the library warns (`refusal-unrecorded`).
- The library's audit log is protected exactly like a project's (R154 a):
  - It is hash-chained and durably appended.
  - It is anchored in this computer's anchors file under `<libraryId>/*`.
  - Every open compares it with that anchor. A broken chain, a changed event, a log cut short, or a missing or emptied log this computer wrote to raises the library-wide warning (`chain-broken`, `head-mismatch`, `truncated`, `empty` or `anchor-missing`). When writable, the open records what it found in the log (`audit.anchor-mismatch` or `audit.anchor-missing`) before anchoring it again.
  - An incomplete last line left by a crash is trimmed at a writable open, and the trim is recorded (`audit.trimmed-incomplete-line`, with size and hash).
  - Repeated refusals (R154 a as amended, N6): the day's first refusal of a kind is a normal chained entry. A later identical refusal that UTC day is dropped, not counted: nothing about it is kept outside the chain. The audit screen says, for each refusal, that further identical ones that day are not listed. "Identical" means every field the entry shows is equal: action, actor, device, decision and every detail, `encrypted` included. Anything that differs is a new entry.
  - The head is kept in memory, so an append does not read the log.
  - The service reads it (`GET /libraries/audit`) and verifies it (`GET /libraries/audit/verify`), with the UI token only. The audit screen shows it.
- No absolute path is ever stored in a log (N5). Text the system produces from an operating-system or library error is scrubbed where that error is captured, before it becomes a recorded reason. That covers the policy check's "could not be evaluated" reason (`repo/mutate.ts`, `move.ts`) and the error codes kept by marks and the library-log set-aside (`reasonOf`). What the researcher typed (names, reasons, notes) is never rewritten, and nothing is scrubbed as a blanket step when an event is appended (R2).
- Known limit (R4): while a project's audit log does not verify and its governance file cannot be read, a set-aside on the library-log path is refused (fail closed), so that project's marks stay until either is repaired.
- Never silent (R28, R82, R154; Task 50).
  - A library move refused by a project's residency rules is audited in each refused project as a `move` deny: who, the destination's kind, its location hint and the rule's reason.
  - Sometimes an action has already happened and only its audit event cannot be written: a library move, split or old-copy deletion, a reconnect, a relink, or a move refused with no open repo. The action is not undone. The project is marked as needing attention with a record in `<Project>/attention/<id>.json`: owner-only, holding the action, its details, when, who and an error code, never a message or an absolute path.
  - A relink writes its record before each copy, naming the file first, so a crash between a copy and its audit event is still recorded, marked as interrupted. A move's own journal covers a crash before its record is written: the switch step reruns.
- Records never steer a privileged action (R154 c).
  - An unrecorded event may only name the actions above. Only `move` may carry a refusal, and the details may not carry `txn`, `attentionId` or `recordedLate`.
  - A permissions record names source ids only, never a path or a mode.
  - Anything else in the attention folder is an unrecognised item (N2, N10). That includes a damaged file, a file over 64 KiB, a sync client's conflict copy such as "abc 2.json", a folder, a link, or `attention` itself when it is not a folder. Such an item is never read beyond its size, never followed, never parsed and never acted on. It is listed once by name, with an opaque id (`u-` and a hash of the name), and the project shows `attention-unreadable`.
- Repair. Each writable open of a project whose audit log verifies, and that accepts writes, appends the unrecorded event late.
  - The late event carries `details.recordedLate`: when it happened, why it was late, whether it was interrupted, and `by`, the computer recording it now. It also carries `details.attentionId`, so a repair is never recorded twice.
  - A file restored without owner-only permissions is restricted again to owner read and write at most. The repair never adds a bit and covers every file of the named sources, as the project's own index places them. The result is checked and audited with counts as `library.permissions-restricted`.
  - A repair raises `audit-recorded-late`. The audit screen shows late entries with both times.
- Nothing is written under another computer's lock (R154 e).
  - Who holds the lock is checked when a mark is written: the library handle must be open read-write and the lock file must name this computer (N1). It does not matter which repo or library object the caller passed, so the service's read-only session repo writes nothing either.
  - A mark for a library this computer does not hold, or whose project folder cannot take it, waits in this computer's outbox, `<appConfigDir>/attention-outbox/<libraryId>/<id>.json`. It is shown here as `audit-waiting`.
  - It is delivered at this computer's next writable open of that library. It is settled there; or, when the project cannot take the event now, it is moved into the project's folder.
  - Delivery is exactly once (N4):
    - the receiving side recognises every attention id its log already holds, including ids appended earlier in the same pass;
    - an outbox entry whose id the project's folder also holds is the same mark, so the outbox copy is dropped;
    - a copy (outbox or folder) is removed only after its event is durable.
    - The tests crash before the append, after the append, and between moving a mark into the project and removing the outbox copy: the event is recorded once each time.
  - An outbox entry for a project the library no longer has is recorded in the library's log, with `projectMissing`, and then removed (N9).
- Set aside (R154 d). A mark that cannot be repaired can be set aside on the audit screen with a reason.
  - It is decided by `evaluate` as its own operation, `set-aside` (N7). It is allowed in every profile, but the engine itself refuses it without a reason that is non-empty once trimmed, so the decision has substance. That refusal is audited like any other.
  - It is audited with the reason, who, when and the mark itself (its record, or for an unreadable file its size and SHA-256). The record goes in the project's log when that log verifies and accepts writes, else in the library's log.
  - Only then is the mark put aside: moved (renamed) into `<Project>/attention-set-aside/`, never deleted, never followed if it is a link. A refusal is audited, and the mark stays.
  - The audit screen shows, for a set-aside, which mark, the reason, who and when, in both the project's log and the library's log (N3).
  - A mark waiting in this computer's outbox cannot be set aside: it is delivered when the lock is held.
- The banner words each case by its cause. These are the warnings while a mark stands; a mark that is repaired or set aside raises none:
  - `audit-unrecorded`: recorded at the next writable open.
  - `audit-unrecorded-blocked`: the project's log does not verify or a problem is unresolved; set it aside.
  - `attention-unreadable`: an unrecognised item; review and set aside.
  - `permissions-not-set`: retried at each open, or set aside.
  - `audit-waiting`: delivered when this computer next holds the lock.
- Known limits:
  - A crash between a set-aside's audit event and the mark's removal leaves the mark. Setting it aside again records a second event.
  - A reconnect has no intent record: a crash between its work and its event leaves no trace. Reconnect changes no library content.
- Restoring a backup is governed (Task 50b, R138, R174 d, R175, R179 and its fix round 1).
  - **Before anything is written.** `restoreBackup` reads `project.json` and `governance.yaml` from the archive itself, once the archive's names are checked and before its first file is unpacked, and asks `evaluate` (`repo/restore.ts` `decideRestore`), once for the backup's rules and once for the rules the original project has now when it is in the library. A deny from the engine, rules that are missing or cannot be parsed (the backup's, or the original's), an `encrypt` condition on a project that is not encrypted, and a sealed archive whose project is not an encrypted one are all refusals (fail closed). Nothing has been written then, not even the staging folder.
  - **Again at the commit.** The same decision is made in the restore's write-queue turn, before the copy's `project.restored` event is written and the staging folder is renamed into place (R138 c): against the `governance.yaml` as unpacked into the staging folder (the file that would go live), and against the original project's governance read in that turn, which is the governance then in force (ordinary writes, a governance edit among them, are not held up while a backup is unpacked). A restore holds the maintenance lock of the project the backup belongs to: by the manifest for one of the library's own backups, else by the project id the file itself gives.
  - **The record.** An allow is recorded in the copy's own log as its `project.restored` event, which carries the decision and its conditions, `details.op: "project.restore"`, the backup's sha256, `restoredFrom`, `leftOutDestroyed` and, when a project's record of destructions could not be vouched for, `destructionsNotVerified`, or `destructionCertificatesSealed` for locked projects whose sealed certificates were not read (both below). A refusal is a `restore` deny with the reason and `details`: `op`, `backupSha256`, `file` (only for one of the library's own backups), and `at` (`decision` or `commit`). It goes to the log of the project the backup belongs to, when that project is in the library and its log is intact and accepts writes; else to the library's log, with the project's `name` and `encrypted`, where an identical refusal that day is listed once. "Intact" is checked when the refusal is recorded, in the write queue, by reading the log: its chain verifies and it ends at the head the process holds (fix round 1, M4), so a log changed outside the app while it runs is never appended to. The library's entry says why the project's log did not take it: `projectLogNotIntact`, or `projectLogNotWritable` (an interrupted write is pending, or the append failed). If neither can be written the refusal stands and the library warns (`refusal-unrecorded`). No path is recorded. A refused restore writes nothing but that entry. The one thing that may be written besides is not the restore's: a backups manifest that was missing or damaged is rebuilt first, as before every decision that reads it (R92, D15; M3).
  - **A restore never changes any project's lock state (fix round 1, I1).** A sealed backup needs its project's key. When the key ring does not hold it, the key is derived from the passphrase or recovery code given to the restore, against the key file the backups manifest kept. That key is held by the `restoreBackup` call alone: it opens the sealed archive (`keyOf`), reaches the commit turn as `StagedRestore.key` to read and seal the copy's files, is never put in the key ring, and is zeroed when the call ends. So no `key.unlock` happens without its record, because none happens: allowed, refused or failed, every project is as locked or unlocked afterwards as before, and nothing is readable that was not. The copy shares the key id of the project it was made from, so it is locked until it is unlocked itself (`unlockProject`, audited). It is indexed as any locked project is (`IndexSink.indexLockedProject`: the project row marked locked and its manifest's sources, R30). When the key ring already holds the key, the project was unlocked before and stays so, and the copy is open with it, as before.
  - **A locked original at the decision (I1).** `governance.yaml` and the audit log are not sealed, so the decision is made for a locked original exactly as for an unlocked one: both sets of rules are asked, and the destroyed assets are known by id from its verified log. Only its sealed certificates are not read, so their sha256 list cannot catch the same file under another id. That is said in the restore's notes ("unlock that project and restore the backup again") and recorded in `project.restored` as `destructionCertificatesSealed` (project ids). An entry written before `destroyedAssets` existed needs the sealed certificate: for the backup's own project that is a refusal (fail closed) whose message names both ways out, another library or unlocking that project.
  - **A file that is not a readable backup (R179).** No `project.json` or one that cannot be read, an unsafe or unreadable archive, a sealed file that cannot be decrypted, a file changed since it was made, two entries of one name, or an audit chain inside it that does not verify: refused with `UnreadableBackupError` (a `RestoreError`), `UnsafeFileError` or `AuditChainInvalidError` as before, and now audited. There is no project to decide about, so the entry goes to the library's log: a `restore` deny with the plain reason and `details`: `op`, `notABackup: true`, `file` (the base name, never a path), `backupSha256` and `sha256Covers: "the whole file"`. The whole file is hashed because a restore hashes it first in any case. A file that cannot be read at all is recorded with `sha256Covers: "nothing: the file could not be read"` and no hash. A missing key or passphrase, a wrong passphrase and a full disk are not refusals of the file and are not audited (a wrong passphrase is not audited at an unlock either).
  - **Every refusal says which rule and what to do (R179).** The engine's residency reasons for a restore name the rule ("the rule on where data may live in this backup's own rules", or "... that the original project has now") and the way out (another library; for the original's rules also changing them). The original's rules that cannot be read: "Repair that project's rules in the governance editor, or restore this backup into another library."
  - **What is not brought back (R174 d, R179).** A destruction's commit event (`delete`, op `retention.destroy`) now also names the destroyed assets, `destroyedAssets`: ids only, so nothing identifying enters the log of an encrypted project. A restore reads every project's audit log in the library, in full and with the chain verified (`restore-record.ts` `destroyedOnRecord`), before anything is unpacked and again in the commit turn (only projects whose log moved meanwhile are read again). An asset is left out when a destruction's event names its id, or when its sha256 is listed by a certificate that is byte for byte the file the event recorded. The second catches the same file under other ids, in a copy made by an earlier restore. An event written before `destroyedAssets` existed is read from its certificate while that verifies. A certificate that is missing or changed costs nothing: the ids come from the log, and it is said in the restore's notes only when a file was left out on that destruction's account. A certificate-named file a verified log does not record counts for nothing, and is said only when it names a file the restore brought back. The restore answers with `leftOut` (source, asset, when destroyed) and a plain note.
  - **Whose audit log must verify (R179).** "Verify" means the chain holds and the log ends at the head the process holds.
    - *The project the backup belongs to* (the project id in the backup's `project.json`), when it is in the library. If its log does not verify, or records a destruction without `destroyedAssets` whose certificate does not verify either, what it destroyed cannot be known: the restore is refused with `DestructionRecordError`, a `RestoreError` whose message names the project and the way out (the backup can be restored into another library). The refusal is audited, never in the log that does not verify.
    - *Any other project (R179; widened in fix round 1, ruling 2).* The restore is not refused: one damaged log would otherwise stop every restore into the library, and the same backup restores into a fresh library anyway. Unverified evidence excludes, whatever its form (`basis: "unverified"`, `restore-record.ts` `unvouched`): every asset id that a destruction entry still readable in that log names (`destroyedAssets` of a `delete` event with op `retention.destroy`; a line that cannot be parsed gives nothing), and every asset id and sha256 that the project's certificate and amendment files name, taken as they are on disk. It never brings data back. A verified record decides first, so such evidence only ever adds to what is left out. The accepted cost: a garbled or forged log or certificate can keep a file out wrongly; the restore says what it relied on, and the backup restores into another library. Such evidence is read again in the commit turn, never reused from the first reading, because nothing ties it to the head the process holds. The restore's notes say that this project's audit log did not hold together and what the exclusion rests on. The copy's `project.restored` event records the same in `destructionsNotVerified`: `projectId`, `leftOut`, and `basis`: `unverified-log-and-certificate-files`, `unverified-log-entries`, `certificate-files-alone` or `nothing-could-be-read` (a file or entry that names no asset is no evidence of what was destroyed). An entry in a verifying log that names no files and whose certificate does not verify is recorded there too, with its `certificate`.
    - *A folder that could not be loaded (fix round 1, ruling 3).* A directory in `Projects/` whose `project.json` is missing or cannot be parsed is not in `listProjects()`, but whatever of its `audit/` and `retention/` can be read is used exactly as above (a sealed certificate only with a key already in the key ring). It never refuses a restore: it may be the very project that is being recovered, and with no `project.json` the decision asks the backup's own rules alone. The notes say that the folder could not be loaded, and `destructionsNotVerified` holds `{ folder, notLoaded: true, basis, leftOut }` (the folder's name, not a path). Left alone: hidden folders (a project in the making), a project moved to another library, a folder with a readable `project.json` (a project, loaded or about to be), and a folder that holds neither an audit log nor retention records.
  - **The inherited warning (R175).** The backups a copy inherits as still to be removed are noted for it in `Backups/backups-state.json`, in the commit turn, as the last step before the rename, from the audit events the copy starts with (`restore-record.ts` `inheritedOutstanding`, on the fold the retry uses). The note is taken back if the rename fails. So the copy's `destruction-backups-pending` warning stands from the moment it exists, and the restore's answer carries it. It is not written in a project transaction, because the state file lives outside every project folder. No retry pass is run by the restore: a pass makes a backup and removes files, and the copy settles its list on its own passes, as R175 says. A crash between the note and the rename leaves a note for a project that was never made, which nothing reads.
  - **Where the reading lives.** The fold of audit events into destructions and the readers of the certificate files are in `destruction-record.ts`, moved out of `retention.ts` unchanged. The retry (`retention.ts`) and the restore's readers (`restore-record.ts`) both build on it. `export/backup.ts` imports `restore-record.ts`, and neither of the two new modules imports `backup.ts` or `retention.ts`, so the restore does not depend on the module that depends on it.
- Repository writes use a write-ahead marker (`<Library>/.tmp/txn-<id>.json`, see `repo/txn.ts`). Every allow event of a write carries `details.txn`. If a crash interrupts a write before all its allow events are appended, the next writable open rolls the write back and reports `rolled-back-incomplete-write`. Data never stays live without its audit record.
- Backups after R138 work as follows.
  - **Maintenance lock.** A backup, a prune, a restore and a destruction of raw data run one at a time per project. This is an in-process maintenance lock, and it is not the write queue, so ordinary writes go on. Holding it is explicit: a section is given a hold that is valid only while the section runs, and it passes that hold to the steps it makes itself (destruction's fresh backup and prune). Work scheduled from inside a section, such as a timer, does not inherit the hold; it waits for the lock like anyone else.
  - **Name.** The backup name is reserved in `pending` before the zip is written. The finished temp file gets that name through a hard link, never by replacing an existing file. Where links are not supported, it is renamed after a check made under the manifest queue. The file is then hashed again under its new name.
  - **Commit turn.** The `backup.create` event is appended in one write-queue turn, together with two checks made in that turn:
    - the same decision, evaluated again against the governance in force at that moment (a deny is audited);
    - a check that no asset the snapshot held has since been destroyed.

    If either check fails, the archive is removed and nothing is recorded as a backup.
  - **Destruction under retention.** Destruction removes every backup that holds a destroyed asset, whether or not its fresh backup can be made. If none can be made, the destruction's record says so.
  - **The manifest is rebuilt when it is missing (D15, R174 c).** `Backups/backups-manifest.json` is read through one loader. A manifest that is absent while backup-named files are in the folder is rebuilt exactly as a damaged one is (R92): each file's entry from its own `backup.json`, and a file that cannot be read listed as `unresolved`, which a destruction then lists as `backupsUnreadable` (status `unknown-pending`, the warning raised). Every decision that depends on the manifest goes through that loader (a destruction's list, a retry pass, a prune, a restore's choice of backup), so the rebuild always comes first. "No backups" is concluded only from a folder that holds no backup-named file; a folder that cannot be listed is an error. A rebuild leaves out an archive that has its name but whose backup is not settled yet (it is in `pending`): settling lists it or removes it, by what the audit log says. A backup that takes the name of one removed outside the app replaces that manifest entry. A manifest that is present and well-formed but lists fewer backups than the folder holds is still believed, as before.
  - **Which backups, and who says so (R147).** The list is decided once, inside the destruction's own change, and recorded in that change's audit event (`delete`, op `retention.destroy`): `certificate` (file name), `certificateSha256`, `backupsToRemove`, and `backupsUnreadable` for project-named files the manifest could not read. The audit log is the authority from then on. An entry leaves the list only through a later `delete` event with op `retention.backups` for the same `certificateSha256`, which names it under `removed` (the app removed it), `noLongerPresent` (it was found missing; never worded as removed) or `notHolding` (an unreadable file that could be read at last and holds none of the destroyed assets). The step's status is derived from the list: `pending` or `unknown-pending` while it has an entry, `deleted` or `no-longer-present` when it is empty. Nothing is derived again from the project's sources.
  - **Certificate and amendments (R147).** The certificate (`retention/destruction-<date>.json`, sealed as `.json.enc` in an encrypted project) is written in the destruction's change and never rewritten, so the sha256 in the audit log keeps verifying. Each later fact is an amendment: a new file beside it, `destruction-<date>.amendment-<n>.json`, with `kind: "destruction-certificate-amendment"`, the certificate's name and sha256, its number, the time, and under `backups` what that step did (`removed`, `noLongerPresent`, `notRemoved` with reasons, `freshBackup` or `freshBackupFailed`, `outstanding`, `status`). An amendment is written in a governed change of its own (R26 marker), and that change's audit event carries `amendment`, `amendmentSha256` and the same facts: the file and its record exist together or not at all. Amendment files were chosen over an append-only log because each is then a whole file with one fingerprint, written and rolled back by the existing transaction, and sealed like any other project file. A `retention.backups` event repeats the facts for readers of the log.
  - **A restored project inherits destructions (R175).** Restore never rewrites the audit log or anything in `retention/`: certificates and amendments are copied byte for byte and go on naming the ids and folder of the project the data was destroyed in, so the sha256 values in the inherited audit events keep verifying (the reader gives `inheritedFrom`). A destruction whose commit event names another project is inherited, and its list with it: the copy settles it as the original would and raises the same warning. Because the copy's log cannot see what the original did after the copy was made (a removal, a later backup under the same name), the copy removes a listed file only when its sha256 is the one the inherited `backup.create` event recorded for that name; a file of another content is a later backup, is never touched, and the listed one is recorded as no longer present; a listed backup whose making the log does not record is left, with a plain reason. The removal holds the maintenance lock of the project the backup belongs to, when it is in the library (R138 a). Original and copy record the step each in their own log: the one that removed the file as `removed`, the other as `noLongerPresent`.
  - **One backup, two destructions.** Within one project, a listed backup that is missing and that the same verified reading records as removed by the app for another destruction (not before this one) is recorded as `removed`, with that record's time, and `removedUnder: { <backup>: { certificate, at } }` in the event (`under` in the amendment); the step then reads `deleted`, not `no-longer-present`.
  - **Conveniences are not authorities (R147).** The certificate, the amendments and `Backups/backups-state.json` are never what a removal is decided from. Before anything is removed on a retry, the whole audit log is read again, its chain verified, and its head compared with the head the process holds. If the certificate or an amendment does not match the sha256 the log holds, or the state file names a backup the log does not, nothing is removed for that destruction, the warning stands and the reason is recorded once (`retention.backups` with `problem`; never with text taken from the state file); a listed backup that is found gone is still recorded as gone. If the log itself does not verify (R174), a pass does none of that: it removes nothing and writes nothing (no amendment, no audit event, no manifest entry cleared), drops nothing from the note behind the warning, whether or not the file is still in `Backups/`, and keeps the plain reason with the warning; the time of the attempt is kept for the back-off. Every pass reads the log cheaply (the lines that matter, not checked against the chain), so whatever a pass would write or drop is preceded, in that pass, by the full reading with the chain check. Both readings run outside the repository's write queue; only the comparison with the head runs in it, and a reading that does not match the head is made once more in the queue, so an entry appended meanwhile is not taken for an outside change. The reader of certificates (`listDestructions`) verifies the chain as well and gives that reason with the status it shows. Raising the warning again rests on the state file or the log's own list: if the log and the state file were both changed, only the check of the chain at the next open reports it. Known limit: an event appended with a valid chain while the app is closed is accepted at the next open, as for every other use of the log (the anchor detects rewrites and truncation, not appends).
- Backups are governed like every other action. Manual and scheduled backups alike are evaluated before anything is written, and a deny is audited (`backup`, with the reason) and creates nothing. Backups are not an exception to the write-ahead rule, but they cannot use the txn marker: the marker may only touch the project's own folder, and a backup is written to `<Library>/Backups/`. They follow the same rule with a record of their own instead, kept in `Backups/backups-state.json` (`pending`). The allow decision is audited first (`backup`, with its conditions and a `backupId`). The zip is then written in full under a temp name and fsynced. **The commit point is the `backup.create` audit event** carrying the same `backupId`. Only after that event is the file renamed to its backup name and listed in the manifest. On the next writable open, and before every backup operation, an interrupted backup is settled by what the audit log says. If the log holds `backup.create`, the backup is renamed and listed. If it does not, the temp file is overwritten and removed and the project shows `backup-failed`. A backup is never named or listed as one without its event. If the event cannot be written, the backup is not kept and `backup-failed` gives the reason (R28, R82). Removing old backups is a plain delete (R91). It is recorded in `pending` before the first file goes and audited afterwards, as one `backup.prune` event naming the files. If a crash or a failed append loses that event, it is written on the next settle (`recovered: true`), and the project shows `backup-audit-pending` until then.
- An audit event or change exists only once its whole line and newline are durably written (R28). A crash during an append outside a transaction (a deny event, an unlock, an integrity event written at open) can leave an incomplete last line and no marker. The next writable open removes such a line from a project's last audit segment and its change logs, reports `trimmed-incomplete-audit-line`, and records `audit.trimmed-incomplete-line` with the file, byte count and SHA-256 of the removed bytes. A read-only open, or a project with an unresolved marker, only reports it (`incomplete-audit-line-pending`). An audit append that fails while opening blocks that project only, never the whole library.
