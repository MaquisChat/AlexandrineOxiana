# Zotero Account Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** The researcher's chosen Zotero libraries (personal and group) come into their projects by themselves while the app is open: the first time in full, then only what changed in Zotero. Nothing in Zotero is ever changed, and nothing here is ever deleted or overwritten because Zotero says so. Every run ends in a plain record that the researcher can read.
**Architecture:** A library-side runner, `syncZoteroLibrary`, wraps the existing Web import (`startZoteroWebImport` / `resumeBatch`) and adds three things: a cheap "has anything changed?" check that answers 304, so a quiet run writes nothing; the pick-up of its own unfinished batch; and a run record kept in a per-device history file. The import itself is made fit to run unattended. It sees Zotero's bin and deletions and marks them. It never downloads a file twice. It turns a field changed on both sides into a review entry for the researcher. It records the library version on resume too. The service exposes manual runs, settings, a key check and status, and a scheduler (added last) starts runs only when the researcher has switched automatic sync on. A new screen, `/settings/zotero`, shows and controls all of it.
**Tech Stack:** undici 8.12.3 (`packages/library/package.json:27`; MockAgent for unit tests), @napi-rs/keyring 2.1.2 (`:18`), Fastify 5.12.7, React 19.3.1, msw 2.15.0, Vitest 3.2.7, @playwright/test 1.63.0 (Chromium and WebKit). No new dependency.
**Spec:** docs/handoff/SPEC.md §5.1 table "Zotero import" (line 255); §5.4 Bulk Import, sources and steps 6–7 (lines 297–327), "Zotero specifics", incremental re-import "so the researcher can keep using Zotero during the transition" (lines 329–332); §2.3 Sync model, which is device sync and stays out of scope (lines 86–92); §6.1 single policy checkpoint (lines 469–475); §9 platform failures "shown clearly with retry", "Governance fails closed" (lines 593–594); §10 "incremental Zotero re-import … interrupt-and-resume … 10,000+ items" (line 607).

## What exists today
- The Web import reads only `https://api.zotero.org` (`zotero-web.ts:59`), with the key in a header and read from the keyring when the scan starts (`:652-664`). It honours Backoff and retries 429 and 5xx up to 5 times, with waits capped at 2 minutes (`:205-258`). Pages hold 100 items (`:432-443`). A JSON page is capped at 10 MB and a file at 2 GB (`:70-71`).
- Incremental by Zotero library version. `since` comes from `project.json importSettings.zoteroWeb[ref].lastLibraryVersion` (`core/src/model/project.ts:34-39`, `zotero-web.ts:886-890`). `/items?since=` brings in each changed item's whole tree (`:489-537`). Every request is pinned with If-Unmodified-Since-Version, and a library that changes mid-scan restarts the scan at most 3 times (`:261-275`, `:672-684`; R80).
- Matching is by version identity `<ref>/<itemKey>` and a token over the versions of the item and its children (`:722`, `:825`, `:838`). The engine looks these up in the journals of every non-undone batch of the kind (`bulk/run.ts:1629-1642`): unchanged → `unchanged`, changed → `update()` (`run.ts:739-747`).
- `since` moves on only after a finished batch in which nothing failed and every download succeeded (`zotero-web.ts:922-933`; R80 I1). It is recorded as a governed write (`repo/import-settings.ts:41-48`). **On resume it is never recorded:** the service resumes through the generic `resumeBatch` (`apps/library-service/src/routes/import.ts:109-126`). `zoteroWebAdapterFor` rebuilds a full scan without `since` (`zotero-web.ts:880-883`).
- **Every run creates a batch** before it reads anything (`run.ts:1718-1739`). A run with nothing new still leaves `imports/batch-NNNN` behind.
- **Files are downloaded inside the scan, before the engine checks its journal** (`zotero-web.ts:734-755` against `run.ts:650-659`). So a resumed batch downloads every file again, and a change to an item's metadata only (a new tag, say) downloads its PDF again; the hash check in `addFiles` then drops the copy (`run.ts:1582-1585`).
- Files are fetched with `GET /items/<key>/file`, which answers 302. The redirect is followed without the key, over https only, to `ZOTERO_STORAGE_HOSTS` = files.zotero.net, zoterofilestorage.s3.amazonaws.com, s3.amazonaws.com, marked UNVERIFIED (`:61-68`; R79). The download checks MD5, free space and compressed ZIPs. A file that is missing (WebDAV), too large or damaged leaves a file note (`:98-105`, R66). **A 403 on `/file` (a key without file access) is treated as a refused key and ends the whole run** (`:319`).
- Notes and annotations: child notes become annotations of kind note, and reader annotations get pdf anchors with the sort index (`:768-782`). A re-import keeps the researcher's recolouring, notes and deletions (`bulk/update.ts:203-258`; R192, R195). An incremental run does not back-fill the sort index (R196 b). Standalone notes, attachment notes, snapshots and linked URLs are only counted (`:23-24`, `:848-853`).
- Collections are read whole on every run (`:539-579`) but **are applied only when a source is created**. An update adds new tags only (`run.ts:1459-1468`). Removals in Zotero are never applied (R73 deferrals).
- **Deletions in Zotero:** `/deleted?since=` is counted in one note and nothing more (`:687-691`, `:117-118`). **The bin is invisible:** requests leave `includeTrashed` at its default of 0, so an item moved to the bin is simply missing from incremental runs, and `Tree.add` drops trashed data (`:455-458`). Deleted here stays deleted, through the R73 tombstones (`run.ts:748-753`).
- **Conflicts:** a field that Zotero changed and the researcher also changed is "kept and reported" in the batch report (`update.ts:105-111`, `run.ts:1463-1466`, `:1605-1612`). Nobody is asked. The capture twin queues such a field for the researcher's decision (`repo/review.ts:148-171`; R190, R193, R194) and settles it through `confirmField` (`source-actions.ts:63-82`; R191).
- **Gone at the source, twin:** a profile capture marks a vanished post `availability: unavailable-on-platform` with `firstNoticedAt` and restores it when the post returns (`capture/profile-capture.ts:590-618`). The interface shows "No longer available at its source, noticed on …" (`ui/src/components/AvailabilityMark.tsx:15-19`).
- **Key:** write-only routes `GET/PUT/DELETE /secrets/zotero-api-key`, UI token only (`routes/zotero.ts:148-178`; R78). One secret name (`secrets.ts:20`). Nothing checks what a key can read. The wizard asks for the numeric library ID by hand (`StepSource.tsx:62`, `:164-183`). The CLI uses `ao secrets set zotero-api-key` and `--web user:<id>` (`apps/cli/src/commands/import.ts:65-89`).
- **Running:** `POST /projects/:id/import` starts a run and `state.followBatch` publishes `import.progress` (`state.ts:893-910`). Shutdown and move suspend batches to `paused` (`state.ts:916`, R99 I4). `GET /jobs` lists live imports (`routes/jobs.ts:26-50`). Nothing schedules a Web import.
- **Network containment** is per request in code (the fixed origin plus the storage-host set). There is no service-wide outbound allowlist. Unit tests run under an undici MockAgent with `disableNetConnect` (`zotero-web.test.ts:40-68`; R79). **No end-to-end stand-in for Zotero's servers exists** (`e2e/import.spec.ts:101-129` uses a local data folder). The precedent for a test-only switch is `AO_LOOKUP_FIXTURES`, which is honoured only under `NODE_ENV=test` (`lookup/recorded.ts:30-31`).
- **Policy:** `sync` is reserved for device sync and always denied (`core/src/governance/engine.ts:409-410`). Imports evaluate `capture` and `store` (`run.ts:372-392`).

## Global Constraints
- **One way.** No request other than GET is ever sent to any Zotero host. A test in Z2 asserts that every request the adapter makes in the whole suite is a GET. A key with write access works, but the screen says it need not have it (Z9).
- **Hosts, exactly.** Requests carrying the key go only to `https://api.zotero.org`. File redirects go only over https on port 443 to `zoteroFileHostAllowed(url)` = host `zoterofilestorage.s3.amazonaws.com`, or host `s3.amazonaws.com` with a path that starts `/zoterofilestorage/`. `files.zotero.net` is removed. No other host: no `stream.zotero.org` (no push), no WebDAV server.
- **Key (R78).** The key lives only in the keyring. It is never sent back, put in a URL, logged, written to a file or entered in an audit entry. The `key` field of `/keys/current` is dropped as soon as it is parsed.
- **Policy.** No new policy action. Runs are import batches (`capture`/`store`, R72/R78). Marks and conflict entries are `store` changes to the source, as `updateSource` does. The action `sync` is not used.
- **R26.** Every library write is one governed change: txn marker, change log, and an audit event carrying `details.txn`. The device files (`zotero-sync.json`, `zotero-sync-history.json`) are not library data. They are written atomically with mode 0600 through `updateAppSettingStrict` (`app-settings.ts:233`).
- **R177 audit.** Kinds, counts, field names and ids only. Never a title, a group name, a value, a host's path or a key.
- **Since.** It is remembered only after the run's changes are written and nothing transient failed. A crash before that repeats the same changes, which are then matched as `unchanged` (no duplicates). The first sync of each link after this plan is a full run (R196 c).
- **Automatic runs.** Off until the researcher turns them on. They run only while the app is open, the library is open read-write and the link's project is unlocked. Intervals are 30, 60 (default) or 240 minutes, never more often than 30. The first automatic run starts 2 minutes after the library opens. Libraries run one at a time.
- **Back-off.** After any `Backoff` or `Retry-After` answer, or a 429 that survives its retries, no run of any kind starts before `backoffUntil` = the later of now + 60 minutes and the server's stated wait. A failure (unreachable, 5xx) only waits for the next interval.
- **Deletions.** Nothing here is deleted, emptied or overwritten because of Zotero. Removed tags, removed collection memberships, deleted notes and deleted highlights are kept here and counted in the run record.
- **Words.** Plain British English. Dates in the form "12 March 2027" (`en-GB`, `dateStyle: "long"`), times as "14:32". Group names and titles go through `UserText`. A failure always names itself and never reads like "up to date".
- **UI (R113, R145).** Colours from theme tokens only; no new token (`tokens.css` belongs to R8). `UserText` for outside text, never `innerHTML`. Everything is reachable by keyboard and named for screen readers. Dialog tests assert `document.activeElement`.
- **Shared types** are declared once in `packages/shared/src/api/zotero-sync.ts` and used by both sides.
- **Tests never touch the network.** Unit tests use `FakeZotero` (Z1) through MockAgent. End-to-end tests use the same model over a loopback HTTP server, reached through switches that are honoured only under `NODE_ENV=test` (Z11).
- **Reader isolation.** Z1–Z11 never touch `packages/ui/src/reader/**`, `screens/Reader.tsx`, `screens/Library.tsx`, `components/SourceTable.tsx` or `theme/tokens.css`.
- Commits end with the session's own trailers. No model identifiers anywhere else.

## Review Focus
1. **A 12,000-item library on the first run, interrupted.** The app closes after 5,000 items. On reopening, the sync resumes its own batch, downloads no file twice, keeps memory bounded and records `since` at the end. Pinned in Z4 by `zotero-web-files.scale.test.ts › "a 12,000-item first sync suspended at 5,000 resumes without fetching any file twice and records the version"`.
2. **The laptop lid closed mid-run.** Requests fail, timers jump and the wake comes hours later. Since stays put, the next run finishes without duplicates, and only one run starts after waking. Pinned in Z7 by `zotero-sync.test.ts › "a run whose network drops mid-page records an honest failure, keeps since, and the next run ends with no duplicate"`, and in Z10 by `zotero-sync-scheduler.test.ts › "after a 5-hour sleep one run starts, not ten"`.
3. **An item deleted, or moved to the bin, in Zotero that the researcher has highlighted here.** It stays, with its highlights and notes untouched, marked "No longer in your Zotero library, noticed on …". Restoring it from the bin removes the mark, and undo puts everything back. Pinned in Z5 by `zotero-gone.test.ts › "a Zotero deletion marks a highlighted source and changes nothing else"` and `"restored from the Zotero bin, the mark goes and the earlier availability returns"`.
4. **A key revoked, or a group the key can no longer read.** The run says so plainly, nothing changes, since stays, other libraries still sync, and that link waits until the key is checked again. Pinned in Z7 by `"a revoked key ends the run with key-refused and pauses automatic runs for every link"` and `"a group the key lost is reported and the personal library still syncs"`.
5. **Files kept on WebDAV, or a key without file access.** References, notes and highlights still come in. Each item says in words where its file is. The run is not a failure and does not retry for ever. Pinned in Z2 by `zotero-web.test.ts › "a 403 on a file is a per-file note, not a refused key"` and `"a WebDAV library's items come in with their highlights, unanchored, and say the file is not in Zotero's online storage"`.

### Task Z4: No file downloaded twice
**Depends:** Z2 **Can run beside:** Z3; R8–R12
**Files:** Modify: `zotero-web.ts`, `bulk/scan.ts`, `bulk/run.ts`, `bulk/batch.ts`, `bulk/update.ts` (`annotationPlan` asset lookup) / Test: `zotero-web.test.ts`, `packages/library/src/import/zotero-web-files.scale.test.ts` (create; in `vitest.scale.config.ts`)
