# PDF Reader and Highlights Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** A researcher opens a source's PDF inside the app, reads it, and makes, recolours, annotates, edits and deletes highlights and page notes, with Zotero's imported highlights shown in place exactly like new ones, in every locked, encrypted and read-only situation.
**Architecture:** The service gains a ranged, token-authenticated byte route for a stored PDF (decrypting as it streams) and governed, audited, crash-safe annotation routes over the existing per-source `annotations.json(.enc)` (R74). The interface renders with pdf.js's core API (no pdf.js viewer, no PDF link or form layer) fed through a `PDFDataRangeTransport` backed by authenticated `fetch` range requests, and draws highlights as its own overlay from one anchor shape: page, rectangles in PDF user space, quote, sort index. Imported and new annotations go through the same model, the same colour mapping and the same overlay code.
**Tech Stack:** pdfjs-dist 6.4.299 (Apache-2.0, legacy build, already pinned at `packages/library/package.json:25`), React 19.3.1, Vite 7.3.8, Fastify (existing), zod (existing), Vitest, Playwright (Chromium + WebKit, `e2e/playwright.config.ts:26-29`), pdf-lib (existing fixture builder, `tests/fixtures/generate.mjs:203`).
**Spec:** docs/handoff/SPEC.md §3.4 Anchor and §3.5 Annotation (lines 125-131); §5 Zotero import of reader annotations (lines 255, 331); §7.1 Phase 3 coding of any anchor (lines 515-521); §8.1 locators carried from annotations (line 535); §8A.1 tokens (lines 564-567), §8A.2 reading-view typeface (line 573), §8A.4 accessibility (lines 581-583); §9 "Originals never modified" (line 589); §11 Phase 3 (line 620).

## Global Constraints
- R26: every annotation change is one `runMutation` (`packages/library/src/repo/mutate.ts:443`): txn marker, change log, audit event carrying `details.txn`; a crash in between rolls back the whole change.
- R74 I4 / R77: annotations live in `<source>/annotations.json` (`annotations.json.enc` sealed when encrypted) written only through `writeSourceFile` (`packages/library/src/repo/sources.ts:255`); caps 10,000 per source and 16 MB of quote+body text (`packages/library/src/import/bulk/update.ts:149-150`); a write over a cap is refused whole, never truncated.
- R96: new routes are UI-token only (`req.caller === "ui"`), loopback, no token or secret in any URL, JSON bodies ≤ 1 MB, errors `{error:{code,message,reason?}}` with no absolute path, mutations through governed library APIs only.
- R113 / R145: colours from theme tokens only (`lint:css`, `lint:colours`); every quote, note, page label and author through `UserText`; never `innerHTML`; every control keyboard-reachable with a visible focus; any dialog or popover test asserts `document.activeElement` on open, Tab, Shift+Tab and close.
- R135 / R140: media tickets are NOT used for PDFs (pdf.js can fetch ranges itself, so the token stays in the `Authorization` header); the ticket rules and `media-src` are untouched.
- R161: no index migration. Annotation text is already indexed per source in chunks (`packages/library/src/index/db.ts:323-345`); each annotation change calls `tx.index((sink) => sink.indexSource(sf))`, which rewrites only changed chunks and keeps the 2 MB per-source index cap.
- R177: an annotation audit entry holds kinds, counts, field names and ids only; never a quote, a note, a colour value typed by anyone, or a page's text.
- Originals are never modified: nothing writes into a PDF; the PDF route is read-only and changes nothing.
- Pinned exactly: `pdfjs-dist` 6.4.299 in both `packages/library` and `packages/ui` (a test keeps them equal); no other new runtime dependency.
- pdf.js options everywhere in the UI: `isEvalSupported: false`, `enableXfa: false`, `useWasm: false`, `useWorkerFetch: false`, `disableAutoFetch: true`, `disableStream: true`, `rangeChunkSize: 1048576`, `cMapUrl: "/pdfjs/cmaps/"`, `cMapPacked: true`, `standardFontDataUrl: "/pdfjs/standard_fonts/"`, `wasmUrl: "/pdfjs/wasm/"`, `iccUrl: "/pdfjs/iccs/"`; the pdf.js annotation layer (links, forms) is never rendered and the scripting sandbox bundle is never loaded.
- Addresses carry ids only: `/reader?project=<id>&source=<id>[&asset=<id>][&annotation=<id>]`; search words never go in an address.
- Wording: plain British English on screen ("colour", "grey"); every string in quotes below is exact; the API field stays `colorName` to match the existing model's `color`.
- Commits end with the session's own trailers; no model identifiers anywhere else.

## Review Focus
1. **Re-import from Zotero after the researcher changed an imported highlight** (soon automatic with "Sync with Zotero now", ledger 2026-11-12 23:55): a recolour or a note must survive a re-import, and a deleted one must not come back. Pinned in R2: `planAnnotations keeps a recoloured imported highlight`, `planAnnotations does not re-add a deleted imported highlight`, `annotationHash of an imported annotation is unchanged by the new optional fields`.
2. **A two-column article**: a mouse selection from the foot of column one to the head of column two must give rectangles on those lines only and the quote in reading order. Pinned in R10: `selectionToPdfRects merges per line and drops the gutter` and e2e `a selection across two columns highlights only the selected lines` (both browsers).
3. **Overlapping highlights and a highlight across a page break**: both overlapping highlights must stay reachable and editable; a selection from page 4 into page 5 is one annotation with two anchors. Pinned in R10: e2e `two overlapping highlights are both offered where they overlap` and `a selection across a page break makes one highlight on two pages`.
4. **A 900-page scanned PDF** (no text, hundreds of MB): memory stays bounded, every page says plainly it has no text, and jumping to page 900 works. Pinned in R7: `PdfPages keeps at most 6 pages rendered`, e2e `a 900-page scan opens, jumps to page 900 and says it has no text`.
5. **The PDF changed on disk after highlights were made** (a linked file edited elsewhere, or a different page count): highlights must not silently mark the wrong words. Pinned in R8: `quoteStillMatches tolerates hyphenation and spacing but not different words`, e2e `a highlight whose text no longer matches says "The text here has changed since this highlight was made."`.

### Task R5: Ranged PDF route and the client's range reader

- Text selection with the trackpad, including a two-column article and a selection across a page break; Retina sharpness at 100% and 200%.
- VoiceOver: reading a page's text, moving through the annotation list, the colour menu and the delete dialog; the "Selected: …" announcements.
- A 300-500 MB scanned PDF in an encrypted project: opening time, scrolling, memory (Activity Monitor), and that locking the project in the library ends the reader.
- Highlights imported from the owner's own Zotero library sit on their words, including rotated pages and books scanned with crop boxes.
- No PDF opens a link, a form or a script, and nothing reaches the network (Little Snitch or the firewall log if available).

## Amendments (they override the task sections above; newest last)

**A1 — Ruling R195 (2026-11-13, after the review of R1): the order of annotations within a page.**
- R1: `compareAnnotations` (or whatever R1 names its comparison) orders by page first. Within one page: if EVERY annotation on that page carries a stored `sortIndex`, they are ordered by it; if any one lacks it, the whole page is ordered geometrically (top to bottom, then left to right, from the anchors' rectangles). The two rules are never mixed within a page, so the order is always total and stable.
- R2: besides keeping Zotero's sort index for newly imported annotations, a re-import fills in the missing `sortIndex` of an annotation that was imported before this plan and is otherwise unchanged — without marking it edited, without changing its hash, and never on an annotation the researcher has changed or deleted. Test first: `a re-import back-fills the sort index of an unchanged imported annotation and reports no change`.
- R10 and R11: every highlight and page note made in the reader stores a `sortIndex` built from its position in the page's text (the same form as Zotero's), so that reading order holds in two-column pages. Test first in R10: `a highlight made in column two sorts after one made at the foot of column one`.

**A2 — Ruling R195 (same date): matching a search hit's words.**
- R1's `matchAnnotations` splits and folds words by the SAME rules as the search index (`packages/library/src/index/text.ts`): punctuation separates words, a query word matches the beginning of a word as the index does, and Chinese, Japanese and Korean text is matched as the index matches it; accent folding never breaks Hangul apart and never makes one kana match another. The rule lives in one place: the pure function is moved to `packages/core` and the library imports it with no change of behaviour (every index test passes untouched), or, if it cannot be moved without changing behaviour, it is replicated in core with a test that holds the two equal over one shared list of examples.

**A3 — What Task R1 exports, as built (2026-11-13).** Wherever a task section above names `annotationSortKey` or `derivedSortIndex`, use this instead; those two no longer exist.
- `sortAnnotations<T extends Annotation>(list: readonly T[]): T[]` — the one way to order a document's annotations (page, then the rule of A1). Every list, overlay and jump order comes from it.
- `matchAnnotations(list: readonly Pick<Annotation, "id" | "quote" | "body">[], words: string): string[]` — ids in the order of the list given, so sort first.
- `pdfSortIndex(...)` and `SORT_INDEX_PATTERN` (building and checking a sort index), the `PdfAnchor` type, `highlightColourOf` and the named colour set as the R1 section gives them.
- The word and CJK splitting used by both the search index and the matcher lives in `packages/core/src/annotations/words.ts` (`latinWords`, `cjkRuns`); `packages/library/src/index/text.ts` imports it. A task that needs to split words uses these and writes no rule of its own.

**A6 — after the review of R6 (2026-11-13; Rulings R199 and R200).**
- R6: the four Liberation Sans font files and `LICENSE_LIBERATION` are NOT bundled (GNU GPL version 2 with a font exception; the project bundles MIT, Apache-2.0 and BSD material only without the owner's decision). `useSystemFonts: true` joins the exact option list, so that pdf.js uses the system's own Helvetica or Arial; on a machine with neither it draws a generic sans-serif face. The unused `iccs/` folder is not bundled either (`iccUrl` leaves the option list). Image limits join the option list with the values R6 settles (`maxImageSize` and `canvasMaxAreaInBytes`), so that one enormous image cannot exhaust memory.
- R6: the worker is created by the app itself (`new Worker(<bundled worker url>, { type: "module" })`) and handed to pdf.js; a "fake worker" (pdf.js parsing on the page's own thread) is refused as an error, never used silently. At `tauri://localhost` the page's origin reads as "null", for which pdf.js would otherwise wrap its worker in a `blob:` address that `script-src 'self'` rightly refuses.
- R6: `PdfHandle` gains a failure channel — `failed: Promise<PdfOpenError>`, which settles when a range is refused or fails after the document was opened (the project locked, the file gone, the service stopped). R7 shows the matching plain sentence and stops asking for ranges; nothing ever waits for ever.
- R6: the licence notices cover every shipped ASSET, one by one (not one per folder), and core-js (MIT), which the legacy build of pdf.js contains.
- R7: replaces the stand-in annotation types in `packages/ui/src/api/reader.ts` by the shared ones of Task R4 (`@ao/shared`), so that a renamed field breaks the interface's build (ledger R184), and consumes `PdfHandle.failed`.

**A7 — after the re-review of R6 (2026-11-13; Ruling R201). It replaces A6's third point where they differ.**
- R6: when a range is refused or fails after the document was opened, pdf.js is NEVER handed made-up bytes (a probe showed page 2 answering with page 7's text after zero bytes were fed in). Instead the document is destroyed at once: `failed` settles with the `PdfOpenError`, the pdf.js document and its worker are destroyed so that every call in flight rejects, and the handle is dead. `PdfHandle` gains `readonly dead: boolean`. To go on, the reader opens the document again from the start.
- R6: a `Worker` constructor that throws (a policy refusal in WebKit) is a `PdfOpenError` of kind "other", like every other way the worker can fail to start.
- R6: the image limits are `maxImageSize: 268435456` (2^28 pixels) and `canvasMaxAreaInBytes: 268435456` (2^28 bytes), so that a 600 dpi A4 scan is drawn at full size (about 35 megapixels) and a 600 dpi A3 scan or a 1200 dpi bitonal A4 page is drawn, scaled down to the canvas limit of about 67 megapixels, rather than left out. (Corrected after fix round 2: the first wording said "at full size" for all three.) If pdf.js 6.4.299 offers a supported signal that it left a picture out for its size, the handle exposes it so that R7 can say so on the page; if it offers none without patching pdf.js, that is recorded here as a known limit: a page whose only picture is larger than 268 megapixels is drawn blank.
- R7 (binding): every read from a `PdfHandle` (a page, its text, a render) is raced against `failed`. On `failed`: every render is cancelled; every canvas and text layer of that document is cleared; every result that arrives afterwards is dropped; nothing from that handle is ever stored (no quote, no rectangle, no sort index); the handle is destroyed and never reused; the screen shows the plain sentence for the failure and "Open again". Tests first: a 423 on a later range while a page is rendering leaves no drawn page and no text behind, and a highlight cannot be made from that document until it is opened again.
- R8, R10, R11: a highlight is only ever made from a live handle (`dead === false`), checked again at the moment of saving.
